# خطة اختبار شاملة للمشروع

**المشروع:** `low-laravel-rectjs`  
**نوع الوثيقة:** خطة تحقق وظيفي وتقني وأمني وتشغيلي.  
**إصدار الخطة:** 1.0 — 28 أغسطس 2026.  
**أساس النطاق:** نتائج تقرير التدقيق للقراءة فقط المرفق.  

## 1. الهدف

تهدف هذه الخطة إلى التحقق المنهجي من أن الأزرار والتدفقات التي رُصدت فيها فجوات أو مخاطر تعمل بصورة صحيحة وآمنة في بيئة اختبار معزولة. وهي لا تفترض وجود عطل في الإنتاج؛ بل تحول الاستنتاجات الثابتة من مراجعة الشفرة إلى حالات اختبار قابلة للتكرار، وتفصل بين **السلوك المتوقع** و**النتيجة الفعلية** و**الأثر التشغيلي**.

> **قاعدة القرار:** لا يعد الزر أو التدفق ناجحاً لمجرد ظهور رسالة نجاح في الواجهة. يجب أن تتطابق الرسالة مع استجابة الخادم، وسجل البيانات، وحالة البث أو التكامل الخارجي عند انطباقه.

## 2. النطاق والأولويات

تغطي الخطة 67 حالة اختبار موزعة على الواجهة، وتنفيذ الطلبات، والفوترة، والصلاحيات، والبث الفوري، وZoom، والذكاء الاصطناعي، والطابور والمجدول. لا تدخل في نطاقها اختبارات الأداء العامة أو اختبارات كل شاشة غير مرتبطة بالمخاطر المرصودة، إلا عندما تكون ضرورية لاختبار انحدار الوظيفة بعد الإصلاح.

| الأولوية | الغرض | قاعدة الإغلاق |
|---|---|---|
| **P0** | يمنع تسرب بيانات، خطأ مالي، مسار دفع خاطئ، أو تعطيل جوهري لتدفق المستخدم | يجب أن ينجح بالكامل قبل النشر أو إعادة الفتح للمستخدمين |
| **P1** | يضمن اكتمال تدفق مهم أو صحة البيانات المعروضة أو استمرارية الخدمة | يعالج قبل إصدار الإنتاج التالي، مع استثناء موثق من مالك المنتج |
| **P2** | يحسن وضوح الواجهة أو تجربة الاستخدام دون تغيير سلامة البيانات | يخطط له ضمن تحسينات المنتج، ولا يحجب النشر وحده |

## 3. المخاطر التي تقود الاختبارات

تستهدف الخطة بشكل خاص اتساق الصلاحيات بين HTTP والبث، تزامن دفعات البوابة، بناء عناوين العودة خلف البروكسي، شفافية نتائج الذكاء الاصطناعي الاحتياطية، حالات مستندات التنفيذ، وأزرار الفواتير والإشعارات. هذه البنود مشتقة من التقرير الاستقصائي السابق، ومن ثم يجب قراءة الحالات المرتبطة بها باعتبارها تحققاً من المخاطر لا ادعاءً بأن حادثة إنتاج مؤكدة قد وقعت.[1]

| رمز الخطر | الخطر المختبر | المسارات/العناصر الرئيسة | حالات الاختبار المحورية |
|---|---|---|---|
| R-01 | تجاوز تفويض البث للصلاحيات الدقيقة أو للحسابات الموقوفة | القنوات الخاصة، جلسات WebSocket | AUTH-02 إلى AUTH-05، RT-04 إلى RT-07 |
| R-02 | تكرار أو تضارب تسوية الدفع | Webhook وCallback وتحصيل الإدارة | PAY-01 إلى PAY-09، UI-INV-07 وUI-INV-08 |
| R-03 | رابط عودة دفع مبني على مضيف غير موثوق | Checkout للفواتير والتنفيذ | PAY-08 |
| R-04 | تسمية معالجة احتياطية كتحليل ذكاء فعلي | طلب التنفيذ والمستندات | AI-01 إلى AI-05 |
| R-05 | حالة مستند لا تتحدث لحظياً | رفع/قبول/رفض مستند التنفيذ | UI-EXE-04 إلى UI-EXE-07، RT-02 وRT-03 |
| R-06 | انتقال إشعار إلى الوجهة الخاطئة | مركز الإشعارات | UI-NOT-01 إلى UI-NOT-04 |
| R-07 | واجهة توحي بنجاح لا يوافق نتيجة الخادم | تحصيل يدوي، تسعير، رفض إثبات | UI-INV-05 إلى UI-INV-08، UI-EXE-08 |
| R-08 | اعتماد الأعمال المؤجلة على عامل ومجدول | Queue، Jobs، الأوامر المجدولة | OPS-01 إلى OPS-06، ZOOM-05 إلى ZOOM-08 |

## 4. بيئة الاختبار والضوابط

يجب إنشاء بيئة **Staging** مستقلة عن الإنتاج، مع قاعدة بيانات اختبار منفصلة وتخزين ملفات منفصل ونطاق اختبار ثابت. تستخدم مفاتيح Sandbox فقط لـMoyasar، وحساب Zoom تجريبي أو محاكيات موقعة، ومزود ذكاء اصطناعي وهمي أو Proxy يعيد استجابات محددة. يمنع استخدام أرقام هوية حقيقية أو وثائق قانونية فعلية أو رموز وصول إنتاجية.

| المورد | متطلب الاختبار | سبب الضبط |
|---|---|---|
| قاعدة البيانات | بيانات قابلة للمسح والاسترجاع، مع لقطة قبل كل دورة P0 | ضمان التكرار ومنع التلوث بين الحالات |
| بوابة الدفع | مفاتيح اختبار وحمولة Webhook/Callback مصطنعة | منع أي حركة مالية حقيقية |
| البث الفوري | خادم Reverb/Pusher اختبار وسجل اشتراكات | إثبات من استلم الحدث فعلياً |
| Zoom | حساب تجريبي أو طلبات موقعة مولدة محلياً | اختبار التوقيع والأحداث بلا جلسات حقيقية |
| الذكاء الاصطناعي | Mock/Proxy واستجابات نجاح وفشل وJSON غير صالح | جعل الفشل قابلاً للتكرار وعدم تسريب بيانات |
| Queue وScheduler | عاملان منفصلان ومراقبة `jobs` و`failed_jobs` | إثبات التنفيذ المؤجل والاسترداد من الفشل |
| المتصفح | Chrome/Edge حديثان على سطح مكتب وجوال | تغطية سلوك الأزرار والرفع والـInertia |

لا بد من إخفاء أي سر أو Cookie أو رمز توقيع من لقطات HAR، وسجلات الاختبار، ومرفقات عيوب الجودة. وتفحص الطلبات المسجلة داخل بيئة الاختبار فقط.

## 5. بيانات الاختبار والأدوار

تستخدم حالات الاختبار ستة حسابات وكيانات معيارية ثابتة. يسمح ذلك بالتحقق من الملكية والصلاحيات والتبادل الفوري في الوقت نفسه.

| الرمز | الحساب أو الكيان | الاستخدام |
|---|---|---|
| U-ADM | مدير نشط | التحصيل اليدوي، إيقاف الحسابات، مراجعة الإثباتات والمستندات |
| U-EMP-LOW | موظف محدود | اختبار منع الوصول إلى HTTP وقنوات البث |
| U-EMP-CASE | موظف قضايا | اختبار الوصول المسموح لمورد محدد |
| U-LAW | محامٍ معيّن | اختبار الملكية والتعامل مع التنفيذ والمستندات |
| U-CLI-A | عميل أ | مالك التنفيذ والفاتورة وتدفقات العميل |
| U-CLI-B | عميل ب | التحقق من العزل ومنع تسرب البيانات |
| EX-01 | طلب تنفيذ | يحوي مستنداً مطلوباً وآخر مرفوعاً |
| INV-DUE / INV-PROOF / INV-PAID | ثلاث فواتير اختبار | تغطية المستحق والإثبات والمدفوع |

## 6. منهج التنفيذ

يبدأ المختبر بحالات **P0**؛ إذ تمثل بوابة النشر. تنفذ الاختبارات اليدوية في المتصفح باستخدام نافذتين مستقلتين أو ملفي مستخدم منفصلين عند اختبار البث والعزل. وتنفذ اختبارات Webhook والتزامن عبر عميل HTTP أو أداة ضغط تدعم حاجز تزامن حقيقياً، ولا تكفي إعادة الطلبات متتابعة لاكتشاف السباق المالي.

ينبغي تشغيل كل حالة ببيانات جديدة أو بعد إعادة تهيئة معلنة. بعد كل عملية حرجة، يسجل المختبر استجابة HTTP، حالة قواعد البيانات ذات الصلة، حالة واجهة المستخدم، الإشعار الناتج، وحمولة البث المسموح بعرضها. وتصبح حالة الخادم ومخزن البيانات مصدر الحقيقة عند وجود تعارض مع Toast أو حالة واجهة.

| المرحلة | التسلسل | المخرج المطلوب |
|---|---|---|
| 1 | Smoke للمصادقة والأدوار ثم الصحة العامة للمتصفح | تأكيد أن البيئة قابلة للاختبار |
| 2 | P0: صلاحيات، بث، دفع، إثباتات، وربط الإشعارات | تقرير نجاح/فشل حاسم للنشر |
| 3 | P1: تنفيذ، Zoom، AI، التسجيلات، PDF، والجدولة | تفاصيل التدفقات ونتائج الاسترداد |
| 4 | P2: رسائل الواجهة، السحب والإفلات، والتحقق المسبق | قائمة تحسينات تجربة المستخدم |
| 5 | إعادة اختبار العيوب وإعادة انحدار مساراتها | مصفوفة تتبع للإغلاق أو الإبقاء |

### 7.1 ملاحظات التنفيذ للأزرار التي رُصدت ناقصة

| الزر أو العملية | ما يجب إثباته في الاختبار | حالة الفشل التي لا تقبل |
|---|---|---|
| «ادفع عبر ميسّر» | لا يظهر عند إثبات التحويل، والخادم يرفض الالتفاف عبر POST مباشر | إنشاء جلسة بوابة رغم وجود إثبات معلق |
| «رفع إثبات تحويل بديل» | يرفض المدفوع خادمياً ولا يغير حالة فاتورة مدفوعة | تحويل فاتورة مدفوعة إلى «بانتظار المراجعة» |
| «تحصيل» للإدارة | لا تظهر رسالة نجاح إلا بعد تسوية فعلية | Toast نجاح عند كون الفاتورة محصلة سابقاً |
| «رفض الإثبات» | وجود حقـل سبب اختياري وتمريره في الطلب والإشعار | زر لا يتيح توضيح سبب الرفض رغم دعم الخادم |
| «رفع المستند» للتنفيذ | صيغة/حجم مفهومين، وتحديث مباشر للطرف الآخر | حالة قديمة لدى الطرف المتصل أو زر معلق |
| سحب وإفلات المستند | يعمل فعلاً أو لا تدعي الواجهة دعمه | منطقة سحب لا تستجيب رغم الوعد الظاهر |
| تسعير التنفيذ | تعطيل واضح أو خطأ مفهوم لقيمة صفر/فارغة | نقرة صامتة توحي بعطل الزر |
| إشعار «فاتورة أتعاب التنفيذ» | ينتقل إلى التنفيذ أو الفواتير حسب السياسة | الانتقال إلى صفحة القضايا بسبب كلمة «أتعاب» |

## 8. اختبارات التزامن والدفع

تعد اختبارات الدفع المتزامن عالية الحساسية. تنشأ فاتورة واحدة مستحقة، ثم تطلق عمليتان متوازيتان من حاجز واحد: إحداهما تحاكي Webhook والأخرى Callback أو Webhook ثانياً بمعرف دفع مختلف. يعاد السيناريو عشر مرات على الأقل بعد إعادة تهيئة البيانات. يجب تثبيت أحد السلوكيات التالية بوضوح: قبول دفعة واحدة فقط، أو حفظ الثانية كحدث تكرار/نزاع، أو رفضها. لا يقبل فقد مرجع دفع أو استبداله صامتاً.

> **شرط قبول حاسم:** العدد النهائي لقيود التحصيل والإجراءات التابعة والإشعارات يجب أن يساوي الأثر القانوني والمالي الصحيح للعملية الواحدة، مهما كان ترتيب وصول الأحداث.

## 9. اختبارات البث الفوري والتفويض

تستخدم نافذتان على الأقل، إحداهما لصاحب المورد أو الفريق المخول والأخرى لمستخدم لا يملك الصلاحية. تسجل محاولة المصادقة للقناة قبل الاشتراك، ثم يطلق حدث حقيقي من حساب مخول. نجاح شاشة HTTP لا يعتبر دليلاً على صحة تفويض البث، ويجب التحقق من رفض الاشتراك نفسه ومن عدم وصول payload لاحق.

تختبر حالة تعليق الحساب بينما الاتصال مفتوح، ثم يطلق حدث جديد. يهدف الاختبار إلى تحديد سياسة النظام المطلوبة: إبطال فوري أو منع الحدث التالي أو آلية انتهاء اتصال محددة زمنياً. يجب توثيق السياسة المتفق عليها قبل الحكم النهائي؛ لأن إيقاف الجلسة عند أول HTTP وحده لا يكفي عند وجود اتصال فوري طويل الأجل.

## 10. اختبارات الذكاء الاصطناعي والحوكمة

تستخدم استجابات اصطناعية منظمة لكل من النجاح، JSON غير الصالح، المهلة، وفشل المزود وعدم تهيئته. لا يختبر المختبر جودة الرأي القانوني بمحتوى حقيقي؛ بل يتحقق من أن حالة المنتج ورسائله تفرق بين تحليل فعلي ونتيجة احتياطية أو حاجة إلى مراجعة بشرية.

كما يفحص Proxy الاختبار الطلبات الصادرة للتأكد من عدم ظهور مفاتيح أو رموز أو بيانات شخصية حساسة في سجلات العميل. أما صلاحية إرسال المستندات إلى مزودي الذكاء الاصطناعي، فتحتاج قراراً من مالك النظام وسياسة خصوصية مكتوبة؛ الاختبار يثبت التنفيذ التقني ولا يمنح موافقة قانونية بحد ذاته.

## 11. معايير القبول والخروج

تتحقق جاهزية النشر عندما تنجح جميع حالات P0 ولا يبقى أي عيب مفتوح من شدة حرجة أو عالية في التدفقات التي اختبرت. ويجوز قبول فشل P1 أو P2 فقط بقرار استثناء مكتوب يحدد الأثر، ومالك القبول، وتاريخ المراجعة، وإجراء تخفيف مؤقت.

| المعيار | شرط النجاح |
|---|---|
| P0 | 100% نجاح أو استثناء موثق من صاحب صلاحية النشر |
| P1 | لا توجد أعطال تمنع تدفق العميل أو الإدارة الأساسي |
| المال | لا ازدواج تسوية أو فقد مرجع أو تضارب في حالة المدفوع |
| الخصوصية | لا اشتراك بث أو تنزيل أو تنقل يكشف مورد عميل آخر |
| العمليات المؤجلة | عامل ومجدول يعملان مع مراقبة واضحة للفشل وإعادة المحاولة |
| قابلية الاستخدام | لا توجد رسالة نجاح كاذبة أو زر صامت في التدفقات ذات الأولوية |
| التوثيق | لكل عيب: معرف حالة، خطوات، دليل منقح، شدة، مالك، وحالة إعادة الاختبار |

## 12. قالب تسجيل العيب

| الحقل | المحتوى المطلوب |
|---|---|
| العنوان | صياغة قصيرة: «[المجال] السلوك غير المتوقع عند…» |
| حالة الاختبار | مثل `PAY-03` أو `UI-NOT-01` |
| البيئة | رابط Staging، رقم البناء، المتصفح/الإصدار، وقت التنفيذ |
| الحساب والبيانات | رمز الحساب وكيان الاختبار فقط، بلا معلومات شخصية حقيقية |
| الخطوات | خطوات مرقمة وقابلة للإعادة من البداية |
| المتوقع/الفعلي | نصان منفصلان، مع مصدر حقيقة خادمي عند اللزوم |
| الشدة والأولوية | حرجة/عالية/متوسطة/منخفضة وP0/P1/P2 |
| الأدلة | لقطة شاشة وHAR/سجل منقح ومعرف طلب إن توفر |
| إعادة الاختبار | النتيجة ورقم البناء بعد الإصلاح |

## 13. مسؤوليات التنفيذ

| الدور | المسؤولية |
|---|---|
| مهندس الجودة | تنفيذ الحالات، حفظ الأدلة المنقحة، فتح العيوب، وإعادة الاختبار |
| مطور الواجهة | تشخيص الرسائل والأزرار وحالات Inertia والبث التي تظهر في العميل |
| مطور الخلفية | مراجعة التسوية، التفويض، الحراس، المعاملات، وJobs |
| مهندس التشغيل | تهيئة Queue وScheduler وProxy والمراقبة والبيانات التجريبية |
| مالك المنتج/المكتب | اعتماد السياسة الخاصة بالمعلومات القانونية والذكاء الاصطناعي، وقبول الاستثناءات |

## 14. المخرجات النهائية

في نهاية التنفيذ، يسلم فريق الاختبار تقرير مرور/فشل حسب الأولوية، ومصفوفة الحالات المحدثة، وسجل العيوب، وقائمة الاستثناءات، ودليل تشغيل Queue/Scheduler. ويرفق التقرير نتيجة إعادة اختبار كل عيب P0/P1، مع دليل يثبت أن الإصلاح لم يكسر مسارات الانحدار ذات الصلة.
