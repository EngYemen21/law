# خطة تطوير الذكاء الاصطناعي في مشروع المكتب القانوني

**إصدار الخطة:** 1.0**الهدف:** تحويل الذكاء الاصطناعي من مجموعة استدعاءات توليدية متفرقة إلى منظومة قانونية **دقيقة، قابلة للمراجعة، محكومة، قابلة للقياس، وآمنة تشغيلياً**.**حد الخطة:** خطة تطوير فقط؛ لا تتضمن تعديلاً برمجياً أو تغييراً في إعدادات المشروع.

## القرار التنفيذي

لو كنت مالك المشروع، فلن أبدأ بإضافة «وكيل ذكي» جديد أو تغيير النموذج مباشرة. الأولوية الصحيحة هي بناء نظام يجعل كل نتيجة قابلة للإجابة عن خمسة أسئلة: **من أنشأها؟ وعلى أي بيانات؟ وبأي نموذج وإصدار Prompt؟ وما مدى الثقة؟ وهل راجعها إنسان؟**. هذه هي النقلة التي تفصل تجربة نموذج تجريبي عن خدمة قانونية قابلة للاعتماد.

يدعم هذا الاتجاه إطار NIST لإدارة مخاطر الذكاء الاصطناعي التوليدي، الذي يركز على دمج اعتبارات الموثوقية عبر دورة حياة النظام، كما تتطلب ممارسات التقييم الناضجة قياساً مستمراً ومراجعة بشرية بدلاً من الاعتماد على الانطباع العام عن جودة الردود.[1] [3]

> **سياسة المنتج المقترحة:** الذكاء الاصطناعي يجهز، ويلخص، ويصنف، ويقترح، ويستخرج؛ أما المحامي أو الموظف المفوض فيعتمد، ويرسل، ويقرر، وينفذ.

## الوضع الحالي: ما يُبنى عليه وما يجب تغييره

المشروع يملك أساساً جيداً: خدمة مركزية، مزوداً أساسياً وآخر احتياطياً، Jobs خلفية، قاطع دائرة للانقطاعات، ومراجعة بشرية في ملخصات التذاكر والاستشارات. لكنه يحتاج إلى فصل أوضح بين **نتيجة AI فعلية** و**Fallback قالبـي**، وإلى قاعدة معرفة قانونية موثقة، وتقييم دوري، وسجل مراقبة شامل. كما أن تحليل التنفيذ قد يبدو ناجحاً عند عودة قالب احتياطي، وأن تصنيف الأولوية/النية لا يتحول دائماً إلى قرار تشغيلي محفوظ.[4]

| المجال | ما هو موجود | الفجوة التي يجب معالجتها أولاً |
| --- | --- | --- |
| تشغيل النماذج | Gemini أساسي وGLM احتياطي | لا توجد بوابة موحدة لكل استدعاء أو سجل جودة وكلفة موحد |
| مخرجات JSON | تعليمات JSON وتحليل يدوي في مواضع متعددة | الحاجة إلى مخططات صارمة وتحقيق برمجي واحد قبل التخزين |
| المراجعة البشرية | اعتماد للملخصات والاستشارات | ضرورة توحيد صندوق المراجعة وحالة كل مخرج |
| المعرفة القانونية | Prompt وسياق ملف العميل | لا تظهر طبقة استرجاع من مصادر قانونية موثقة (RAG) |
| التحمل التشغيلي | Queue وRetry وCooldown | الحاجة إلى قياس SLOs، طوابير مستقلة، ومنع تكرار العمل |
| الخصوصية والأمن | صلاحيات ملفات ومراجع | لا تظهر سياسة كاملة لتصغير البيانات، كشف PII، أو الدفاع ضد Prompt Injection |

## المعمارية المستهدفة

يجب تحويل `LegalAiService` تدريجياً إلى مجموعة طبقات متخصصة، لا إلى خدمة ضخمة تضيف المزيد من الدوال. تبقى واجهات التذاكر والقضايا والاستشارات كما هي من منظور المستخدم، لكن تمر كل الاستدعاءات عبر بوابة خادمية واحدة.

```
واجهة المستخدم / Controllers / Jobs
             │
             ▼
      بوابة الذكاء الاصطناعي
  (توجيه نموذج + مهلة + ميزانية + تتبع)
             │
 ┌───────────┼────────────────┐
 ▼           ▼                ▼
باني السياق  استرجاع قانوني    وكلاء محددو المهمة
والصلاحيات   موثق (RAG)        فرز | وثائق | صياغة | اجتماع | تنفيذ
             │                │
             └──────► بوابة التحقق والسياسة ◄──────┘
                         │
     JSON Schema + مراجع + ثقة + فحص حقن التعليمات
                         │
                         ▼
          مسودة / مراجعة بشرية / قبول محدود / رفض
                         │
                         ▼
        سجل تدقيق + مؤشرات جودة + كلفة + تنبيهات
```

لا ينبغي منح النموذج اتصالاً مباشراً بقاعدة البيانات أو البريد أو الدفع أو Zoom. فكل أداة تنفيذية يجب أن تكون عملية خادمية ضيقة المعلمات، تتحقق من الصلاحيات وقواعد العمل قبل التنفيذ. هذا يعالج مخاطر حقن التعليمات، معالجة المخرجات غير الآمنة، الوكالة الزائدة، والإفصاح الحساس، وهي فئات مركزية في إرشادات OWASP لتأمين تطبيقات LLM.[2]

## الأولويات التنفيذية

### P0 — صحة الحالة، الشفافية، ومنع القرار الخاطئ

هذه المرحلة شرط قبل أي توسع وظيفي. يضاف سجل موحد لكل مخرج باسم مثل `ai_runs` أو `ai_artifacts`، ويحمل نوع المهمة، الملف المرتبط، حالة التنفيذ، مصدر النتيجة، درجة ثقة، إصدار النموذج، إصدار Prompt، زمن المعالجة، وقرار المراجع. حالات المصدر يجب أن تكون صريحة: `ai_success` و`fallback` و`manual_required` و`human_approved`.

تعدل الواجهة بحيث لا تعرض الـFallback كأنه تحليل تم بالذكاء الاصطناعي. في التنفيذ مثلاً، عندما يعود القالب الحتمي، يظهر: **«تقييم أولي آلي محدود — يتطلب مراجعة المستندات»**، ولا يعلّم `ai_done=true`. كما تتحول مهام الاجتماعات إلى «مهام مقترحة» قبل أن تصبح Tasks فعلية، إلا إذا كانت السياسة تسمح بحالة منخفضة المخاطر ومعتمدة مسبقاً.

| معيار قبول P0 | الهدف |
| --- | --- |
| كل نتيجة لها حالة مصدر قابلة للعرض والتدقيق | 100% |
| عرض Fallback كمخرج AI ناجح | 0% |
| اعتماد قانوني أو إرسال رسمي بلا مراجعة مفوضة | 0% |
| إنشاء مهمة حساسة من قرار AI بلا حالة اعتماد | 0% |

### P1 — بوابة موحدة، مخططات صارمة، وإصدارات Prompts

تنشأ بوابة خادمية (`AiGateway`) مسؤولة عن اختيار النموذج وإعادة المحاولة وتهدئة المزود والتتبع. وتستبدل كل استدعاءات النصوص المباشرة بعقود واضحة، مثل: `TicketTriageResult` و`DocumentAnalysisResult` و`ConsultAnalysisResult` و`LegalDraftResult` و`DecisionExtractionResult`.

يجب أن تستخدم المخرجات المنظمة مخططات JSON صارمة مع رفض الحقول غير المتوقعة والتحقق من القيم قبل الحفظ. فمثلاً لا يقبل اقتراح محامٍ إلا إذا كان معرفه موجوداً ونشطاً ومسموحاً له بالقسم، ولا يقبل تصنيف مستند إلا من قاموس أنواع معتمد. كما يوضع كل Prompt في سجل ذي إصدار ومراجع قانوني مالك له وتاريخ اعتماد وسجل تغييرات.

| المهمة | المخرج المطلوب | حاجز التحقق |
| --- | --- | --- |
| فرز تذكرة | قسم، أولوية، نية، سبب، ثقة | قيم مسموحة + حالة تصعيد عندما تنخفض الثقة |
| تحليل مستند | نوع، ملخص، ارتباط، حقائق مقتبسة | مطابقة المصدر + حد الحجم + منع استخدام تعليمات الملف |
| تحليل استشارة | تصنيف، ملخص، نواقص، محام مقترح | محام نشط من القائمة الفعلية + مراجعة موظف |
| صياغة قانونية | مسودة، فراغات، ادعاءات، مراجع | لا اعتماد بلا مصادر قانونية ومراجعة محام |
| اجتماع | ملخص، محضر، قرارات مقترحة | لا قرار غير وارد في النص أو ملخص Zoom |

### P2 — قاعدة معرفة قانونية موثقة (RAG)

لا يكفي توجيه النموذج إلى «استخدام الأنظمة السعودية». يجب بناء مكتبة معرفية معتمدة تبدأ بنطاق صغير: **نظام المعاملات المدنية، نظام الإثبات، نظام المرافعات، نظام التنفيذ، وقوالب المكتب المعتمدة**. كل وثيقة تخزن مع مصدرها، تاريخ السريان، الإصدار، الولاية القضائية، المجال، وتاريخ المراجعة القانونية.

يسترجع النظام المقاطع بعد فلاتر إلزامية: الاختصاص، نوع النزاع، سريان النص، وحدود ملف العميل. وتظهر في صندوق المحامي خريطة داخلية: «الادعاء القانوني ← المرجع ← المقطع». إذا لم توجد مرجعية كافية، ينتج النظام سؤالاً أو تنبيهاً للمراجع، لا رقماً أو مادة متخيلة.

> لا تبدأوا بـFine-tuning. ابدأوا بسياق صحيح، مصادر موثقة، ومخرجات مقيدة. التدريب المخصص لا يصبح مبرراً إلا بعد إثبات أن مشكلة متكررة لا يحلها Prompt أو قواعد العمل أو RAG.

### P3 — التقييم قبل كل تغيير

يبنى مستودع بيانات تقييم مجهّل الهوية من حالات حقيقية راجعها محامون، مع حالات مركبة وناقصة وعدائية. يجب ألا يكون الاختبار «هل تبدو الإجابة جيدة؟»، بل «هل اختار القسم الصحيح؟ هل استخرج الحقائق فقط؟ هل ربط كل ادعاء قانوني بمصدر صحيح؟». توصي أدلة التقييم بأن تكون الاختبارات مهمة-محددة، وأن تجمع التقييم الآلي مع حكم الخبراء، وأن يعاد تشغيلها باستمرار عند تغيير النموذج أو الـPrompt.[3]

| الوظيفة | مؤشر الجودة | عتبة أولية قبل التوسع |
| --- | --- | --- |
| فرز التذاكر | دقة القسم والنية | 90% أو أعلى |
| تحليل المستند | دقة النوع والارتباط | 90% أو أعلى |
| ملخص القضية | عدم إضافة واقعة غير موجودة | 95% اجتياز في عينة محامين |
| الاستشهاد القانوني | صحة المرجع وملاءمته | 95% أو أعلى |
| القرارات من الاجتماعات | عدم خلق قرار/مهمة غير واردة | 98% أو أعلى |
| الاختبارات العدائية | نجاح الحجب أو التصعيد | 100% للحالات المعيارية |

يعتمد التقييم ثلاث طبقات: تحقق آلي من Schema وقواعد العمل، ونموذج حكم مستقل للمقارنة المعيارية، ومراجعة محام لعينة عمياء. لا يستخدم النموذج المنتج نفسه حكماً نهائياً على مخرجاته.

### P4 — تجربة مراجعة بشرية ممتازة

يبنى صندوق مراجعة موحد للمحامي والموظف يعرض المسودة، الحقائق والمستندات التي استندت إليها، درجة الثقة، المراجع القانونية، سبب التصعيد، وسجل الفرق بين المخرج الأصلي وتعديل الإنسان. يوفر قرارات: قبول، تعديل، رفض، طلب إعادة تشغيل، وتصعيد لزميل متخصص. ويطلب سبباً منظماً عند الرفض حتى يتحول إلى بيانات تقييم لا إلى ملاحظة ضائعة.

يستمر الرد الآلي على التذاكر في الحدود منخفضة المخاطر فقط. أما الرأي القانوني واللوائح وصحف الدعاوى والتصنيف المؤثر في المسار القانوني فتتحول إلى **مسودة محامي**. ولا يسمح بتصدير مستند رسمي أو تقديمه أو إرساله إلى العميل بلا اعتماد واضح.

### P5 — الخصوصية والأمن

ينفذ تصنيف للبيانات: عامة، داخلية، سرية، وحساسة جداً. يطبق باني السياق مبدأ «أقل قدر لازم»، فيخفي الهوية والجوال والعناوين والوثائق غير المرتبطة، ويمنع تمرير النصوص غير المطلوبة إلى المزود. وتعامل تعليمات داخل ملفات العميل ورسائله كبيانات فقط، لا كأوامر للنظام.

تشمل الخطة فحص Prompt Injection قبل وبعد الاسترجاع، وتعقيم جميع المخرجات قبل عرضها، ومنع HTML أو الروابط أو تعليمات تنفيذية من المرور مباشرة. كما تعد سياسة احتفاظ ومسح وتشفير وسجل وصول لكل من المدخلات والمخرجات. هذه الضوابط مهمة خصوصاً لأن المشروع يعالج ملفات قانونية ومراسلات وبيانات شخصية.[1] [2]

### P6 — اختيار النماذج والكلفة والاعتمادية

لا يثبت نموذج واحد لكل المهام. يعتمد توجيه متدرج: نموذج سريع ومنخفض الكلفة للفرز والاستخراج، نموذج متعدد الوسائط للمستندات، نموذج أعلى جودة للصياغة القانونية بعد RAG، ونموذج حكم مستقل للتقييم. تمر الحالات منخفضة الثقة أو غير المكتملة فقط إلى نموذج أقوى أو مراجعة بشرية.

يجب أن تعرض لوحة التشغيل لكل وظيفة: نسبة النجاح، نسبة الـFallback، زمن المعالجة P50/P95، عدد الإعادات، الكلفة لكل مهمة، نسبة التعديل البشري، ونسبة الرفض. وينشأ تنبيه إذا قفزت الكلفة أو الفشل أو المدة بشكل غير طبيعي.

| مؤشر تشغيلي | الهدف بعد الاستقرار |
| --- | --- |
| تتبع نموذج/Prompt/زمن/كلفة لكل طلب | 100% |
| Jobs العالقة بلا سبب ظاهر | 0 |
| تغيير نموذج أو Prompt يصل الإنتاج بلا تقييم | 0 |
| مخرجات تصعيد عالية الخطورة تمت مراجعتها | 100% |
| تراجع جودة الإنتاج يكتشف قبل النشر | عبر مجموعة تقييم إلزامية |

## خطة الإطلاق المرحلية

| الإصدار | ما يُفعل | ما لا يُفعل | بوابة النجاح |
| --- | --- | --- | --- |
| 1. داخلي مراقب | سجل AI، حالات المصدر، JSON Schema، القياس | لا تعديل تلقائي لمسارات حساسة | رؤية كاملة للنتائج والفشل |
| 2. اقتراح فقط | فرز تذكرة وتحليل مستندات للمراجعة | لا إحالة أو رفض تلقائي للعميل | تجاوز عتبات الدقة المحددة |
| 3. RAG محدود | التكييف واللوائح وتحليل العقد مع مصادر | لا تعميم على كل الوظائف | اعتماد المحامين للمصادر والمخرجات |
| 4. أتمتة محدودة | إجراءات منخفضة المخاطر ومقيدة بسياسة | لا مستند رسمي/دفع/التزام قانوني آلي | لا حوادث جودة أو أمن في فترة تجريبية |
| 5. توسع متحكم | مزيد من الوكلاء والمهام بعد القياس | لا Multi-Agent واسع بلا دليل | تحسن مثبت في الجودة والوقت والكلفة |

لا أوصي ببناء هيكل متعدد الوكلاء منذ البداية. يبدأ المشروع بوكلاء منفصلين منطقياً مع عقود واضحة، ثم يتوسع فقط إذا أثبتت بيانات التقييم أن المسار الواحد لم يعد كافياً؛ لأن تعدد الوكلاء يضيف نقاطاً جديدة لعدم الحتمية والتسليم الخاطئ بين الوكلاء.[3]

## فريق الملكية والحوكمة

ينشأ اجتماع مراجعة دوري قصير يضم مالك المنتج، محامياً مسؤولاً، مسؤولاً تقنياً، وممثلاً للخصوصية/الأمن. يراجع الاجتماع عينات الرفض، أخطاء الفئات عالية المخاطر، مصادر المعرفة الجديدة، تغييرات النموذج والـPrompt، الكلفة، وحالات التصعيد. القرار في كل دورة يجب أن يكون محدداً: قبول أو إيقاف أو تعديل وظيفة بعينها، لا تقييم عام بأن «الذكاء جيد» أو «غير جيد».

| الدور | المسؤولية |
| --- | --- |
| مالك المنتج | تعريف القيمة وحدود الأتمتة وترتيب الأولويات |
| المحامي المسؤول | اعتماد القوالب والمراجع وRubrics الجودة |
| الفريق التقني | البوابة، التحقق، الطوابير، المراقبة، وسجل التدقيق |
| الأمن والخصوصية | تصنيف البيانات، الاحتفاظ، التحكم بالوصول، والاختبارات العدائية |
| فريق التشغيل | مراجعة التصعيدات وتغذية مجموعة التقييم بأسباب الرفض |

## القرار العملي الأول

أول حزمة تطوير يجب أن تجمع: **حالة مصدر المخرج، بوابة AI موحدة، JSON Schema، سجل تتبع، وإصلاح التمييز بين الـFallback والتحليل الفعلي في التنفيذ**. هذه الحزمة تمنحكم أماناً ووضوحاً فورياً من دون المخاطرة بتغيير تجربة العميل أو إدخال معرفة قانونية غير جاهزة. بعدها تبنى مجموعة التقييم وRAG المحدود، ثم توسع الإمكانات فقط بناء على قياسات فعلية.
