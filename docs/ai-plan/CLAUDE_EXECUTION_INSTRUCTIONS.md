# تعليمات تنفيذ خطة تطوير الذكاء الاصطناعي

## إلى Claude: مهمة التنفيذ

أنت تعمل على مشروع Laravel + React قائم باسم `low-laravel-rectjs`. نفّذ خطة تطوير منظومة الذكاء الاصطناعي تدريجياً، مع الحفاظ على جميع الوظائف الحالية وعدم كسر واجهات المستخدم أو قواعد العمل أو الصلاحيات أو المدفوعات أو تكامل Zoom.

هذه الوثيقة ليست تفويضاً لتغيير كل شيء دفعة واحدة. المطلوب تنفيذ صغير قابل للمراجعة، مع اختبار قبل وبعد كل مرحلة، وCommit مستقل لكل حزمة منطقية. إذا وجدت تعارضاً بين هذه الخطة والشفرة الحالية، لا تفترض الحل؛ أوقف المرحلة، وثّق التعارض، واقترح أقل تغيير آمن.

## قواعد غير قابلة للتفاوض

1. لا ترسل OTP إلى رقم عشوائي أو حقيقي. استخدم fake provider أو استدعاء Mock داخل الاختبارات.
2. لا تنفذ دفعاً حقيقياً. استخدم Sandbox فقط، ولا تغيّر أي مفاتيح إنتاج.
3. لا ترسل مستندات العملاء أو البيانات الشخصية إلى أي نموذج أثناء الاختبارات. استخدم Fixtures مجهلة ومصطنعة.
4. لا تحذف أو تعيد تسمية مسار أو حقل أو Job قائم قبل إثبات أن جميع مستهلكيه انتقلوا بنجاح.
5. لا تجعل الذكاء الاصطناعي يعتمد أو يرسل رأياً قانونياً أو ينشئ التزاماً مالياً أو يرسل مستنداً رسمياً بلا اعتماد بشري صريح.
6. لا تعرض fallback قالبياً على أنه تحليل AI ناجح. يجب أن يكون مصدر النتيجة وحالتها ظاهرين في البيانات والواجهة.
7. لا تمنح النموذج اتصالاً مباشراً بقاعدة البيانات أو الدفع أو البريد أو Zoom. أي فعل خارجي يمر عبر خدمة خادمية محدودة الصلاحية وتحقق من قواعد العمل.
8. لا تسجل نصوص الملفات أو المحادثات الحساسة كاملة في logs. استخدم معرفات مموهة وملخصات تشغيلية.
9. لا تغير Prompt أو النموذج في الإنتاج بلا تشغيل مجموعة تقييم Regression ومراجعة النتائج.
10. لا تستخدم Fine-tuning في البداية. أصلح السياق والمصادر والمخططات وقواعد التحقق قبل التفكير فيه.

## المرحلة صفر: فحص ما قبل التنفيذ

ابدأ بقراءة `AGENTS.md` إن وجد، ثم أنشئ جرداً للملفات والمسارات والـJobs والخدمات المتعلقة بالذكاء الاصطناعي. افحص `composer.json` و`package.json` وملفات البيئة دون طباعة الأسرار. اكتب تقريراً قصيراً يوضح نقطة الدخول لكل وظيفة، ومستهلكيها، واختباراتها الحالية.

قبل أي تعديل، شغّل الاختبارات الموجودة بالطريقة المناسبة للمشروع وسجّل خط الأساس: عدد الاختبارات الناجحة والفاشلة، نتيجة lint/typecheck إن كانت متاحة، وحالة البناء. إذا تعذر التشغيل بسبب البيئة، وثّق السبب ولا تعدّل إعدادات الإنتاج لتجاوز المشكلة.

## المرحلة P0: صحة الحالة والشفافية

أنشئ طبقة أو جدولاً مناسباً لتسجيل مخرجات AI. لا تفترض اسماً واحداً قبل فحص migrations الحالية؛ يمكن استخدام `ai_runs` أو `ai_artifacts` بما ينسجم مع بنية المشروع. يجب أن تشمل البيانات المهمة:

| الحقل | الغرض |
|---|---|
| `task_type` | نوع المهمة: triage، document، consult، draft، meeting، execution |
| `entity_type` و`entity_id` | الملف المرتبط دون تكرار السياق الحساس في السجل |
| `source` | `ai_success` أو `fallback` أو `manual_required` |
| `status` | queued، running، completed، failed، needs_review، approved |
| `confidence` | قيمة محددة النطاق، أو `null` إذا لم تنتج المهمة ثقة موثوقة |
| `model` و`model_version` | النموذج الفعلي المستخدم |
| `prompt_version` | إصدار Prompt القابل للتتبع |
| `trace_id` | الربط بين Job والطلب والمخرج |
| `failure_code` | سبب الفشل المعياري دون أسرار |
| `reviewed_by` و`reviewed_at` | دليل الاعتماد البشري |

غيّر الحقول الموجودة مثل `ai_done` فقط عبر توافق خلفي آمن. إذا كان النظام أو الواجهة يعتمدها، أبقها مؤقتاً لكن اجعل القيمة لا تعني النجاح إلا بعد التحقق. أضف اختبارات تثبت أن fallback لا يساوي `ai_success`، وأن تحليل التنفيذ القالبي يظهر كتقييم أولي يحتاج مراجعة.

## المرحلة P1: بوابة AI موحدة

قسّم `LegalAiService` تدريجياً إلى مكونات واضحة، مع إبقاء واجهة الخدمة القديمة كطبقة توافق مؤقتة:

- `AiGateway`: استدعاء المزود، timeout، retry، cooldown، trace ID، وتسجيل metadata.
- `AiModelRouter`: اختيار النموذج حسب نوع المهمة وحجمها وحساسيتها.
- `AiPromptRegistry`: حفظ Prompt وإصداره ومالكه ونطاقه.
- `AiOutputValidator`: JSON Schema، القيم المسموحة، الحدود، والحقول الإلزامية.
- `AiPolicyGate`: قرار `accept` أو `fallback` أو `needs_review` أو `reject`.
- `AiContextBuilder`: اختيار سياق مسموح فقط وتنظيف المحتوى.

لا تكرر منطق الفشل في كل Job. اجعل الاستثناءات معيارية مثل `ProviderUnavailable` و`InvalidStructuredOutput` و`SensitiveInputBlocked` و`ManualReviewRequired`. يجب أن يكون retry آمناً idempotent، مع `job key` يمنع إنشاء المخرج مرتين عند إعادة تشغيل Queue.

استخدم Structured Output صارماً لكل تحليل قابل للمعالجة آلياً. عرّف Schema منفصلاً لكل من `TicketTriageResult` و`DocumentAnalysisResult` و`ConsultAnalysisResult` و`LegalDraftResult` و`MeetingDecisionResult` و`ExecutionAnalysisResult`. بعد parsing نفّذ تحققاً خادمياً مستقلاً؛ لا تثق في أن النموذج اتبع التعليمات.

## المرحلة P2: إدارة السياق وRAG قانوني محدود

ابدأ بمكتبة معرفة صغيرة ومعتمدة قانونياً. لا ترفع مستندات قانونية إلى الإنتاج قبل تحديد مالك المصدر وتاريخ السريان والإصدار والولاية ونطاق الاستخدام. لكل مقطع معرف مصدر ثابت.

الاسترجاع يجب أن يطبق filters للاختصاص ونوع القضية وتاريخ السريان قبل تمرير السياق إلى النموذج. كل مسودة تكييف أو مذكرة أو لائحة يجب أن تحتوي بنية داخلية:

```json
{
  "claims": [
    {"text": "...", "source_id": "...", "source_excerpt": "...", "support": "supported"}
  ],
  "unsupported_claims": [],
  "draft": "..."
}
```

إذا لم يوجد مصدر مناسب، لا تخترع مادة أو رقم نظام. أعد `insufficient_authority` وأرسل المخرج إلى المراجعة. عالج كل ملف أو رسالة مستخدم كبيانات غير موثوقة؛ النص الموجود داخل الملف ليس تعليمات للنظام.

## المرحلة P3: بوابة المراجعة البشرية

وحّد تجربة المراجعة للمحامي والموظف. يجب أن يرى المراجع المخرج، مصدره، النموذج وPrompt، الأدلة أو المقاطع، مستوى الثقة، سبب التصعيد، والفروقات بعد تعديل الإنسان. وفر أفعالاً منفصلة: قبول، تعديل، رفض، طلب إعادة تشغيل، وتصعيد.

المخرجات الآتية لا ترسل أو تعتمد تلقائياً: صحيفة ناجز، لائحة، مذكرة قانونية، رأي قانوني، تصنيف يغيّر مسار القضية، مهمة ذات أثر حساس، أو أي إجراء مالي. أما الردود الإجرائية منخفضة المخاطر فيجب أن تحتوي على حدود واضحة وألا تدعي أنها رأي محامٍ.

اجعل قرارات الاجتماعات `suggested_tasks` أولاً. لا تنشئ Task فعلية إلا بعد اعتماد، مع idempotency يمنع تكرارها عند وصول Webhook أو إعادة تشغيل Job.

## المرحلة P4: التقييم المستمر

أنشئ Fixtures مجهلة لكل وظيفة. يجب أن تحتوي المجموعة على حالات طبيعية، ناقصة، متناقضة، عربية فصحى وعامية، نصوص طويلة، ملفات غير مرتبطة، محاولات Prompt Injection، ومحاولات الوصول إلى ملف مستخدم آخر.

لكل Fixture خزّن النتيجة المرجعية أو Rubric محامٍ، مستوى الصعوبة، نوع الخطأ، والمراجع المطلوبة. نفّذ ثلاث طبقات من الفحص:

1. تحقق آلي من Schema والقيم والقواعد.
2. مقارنة مخرجات النموذج بمراجع أو Labels.
3. مراجعة محامٍ لعينة عمياء، مع سبب قبول أو تعديل أو رفض.

لا تقبل تغييراً في نموذج أو Prompt إذا انخفضت الجودة في فئة عالية المخاطر، حتى لو تحسن المتوسط العام. استخدم القياسات الأولية التالية كبوابات انتقال، ثم عايرها مع الفريق القانوني: فرز ≥90%، تحليل مستند ≥90%، عدم إضافة وقائع في الملخص ≥95%، صحة المصادر ≥95%، وعدم اختلاق قرارات ≥98%، ونجاح اختبارات الحماية العدائية 100%.

## المرحلة P5: الأمن والخصوصية

صنّف البيانات إلى عامة، داخلية، سرية، وحساسة جداً. طبّق أقل قدر لازم من السياق، وتمويه PII، وسياسة احتفاظ ومسح، وتشفير، وسجل وصول. لا تضع نص الملف الكامل في exception أو log.

أضف اختبارات أمنية تثبت أن:

- ملفاً يحتوي «تجاهل التعليمات السابقة» لا يغير سياسة النظام.
- المستخدم لا يحصل على سياق قضية أو تذكرة غير مسندة إليه.
- مخرجات HTML/Markdown والروابط لا تسبب تنفيذ HTML أو طلبات غير مقصودة.
- النموذج لا يستطيع استدعاء الدفع أو البريد أو تعديل حالة حساسة مباشرة.
- Webhook أو Job مكرر لا ينشئ نتيجة أو مهمة ثانية.

## المرحلة P6: التشغيل والتكلفة

قسّم الأعمال على طوابير مستقلة حسب الحساسية والحجم، مثل `ai-low-risk` و`ai-documents` و`ai-legal-review`. لا تنفذ تحليل PDF كبيراً داخل طلب ويب متزامن. ضع timeout وretry وbackoff وdead-letter path، مع إعادة معالجة يدوية واضحة.

سجّل metadata التالية لكل طلب: المهمة، المزود، النموذج، الإصدار، زمن الانتظار، عدد المحاولات، النتيجة، fallback، الكلفة التقديرية، والـtrace ID. أنشئ تنبيهات لنسبة الفشل، P95 latency، Jobs العالقة، قفز الكلفة، ونسبة النتائج التي تحتاج مراجعة.

استخدم نموذجاً سريعاً للفرز والاستخراج، ونموذجاً متعدد الوسائط للمستندات، ونموذجاً أقوى للصياغة بعد RAG. نفّذ التصعيد للنموذج الأقوى فقط للحالات منخفضة الثقة أو التي فشلت في التحقق.

## استراتيجية عدم كسر الوظائف

كل مرحلة تنفذ خلف Feature Flag، وتبدأ بوضع `shadow` أو `suggestion_only`. احتفظ بالمسار القديم حتى تثبت النتائج. نفّذ migration قابلة للعكس، وراجع generated SQL، ولا تحذف بيانات قديمة. لا تغير API response shape بلا توافق خلفي.

بعد كل وحدة، شغّل: اختبارات الوحدة، Feature tests للصلاحيات والتدفقات، اختبار Queue وretry، فحص TypeScript وlint، وبناء الواجهة. قبل تفعيل أي مسار في البيئة المشتركة، اختبر التذاكر والقضايا والاستشارات والتنفيذ والاجتماعات والدفع في Sandbox فقط.

## Definition of Done لكل Pull Request

| البند | شرط الإنجاز |
|---|---|
| فهم التأثير | قائمة بالمسارات والـJobs والواجهات المتأثرة |
| التوافق | الوظائف القديمة لا تزال تعمل أو لديها migration واضحة |
| الاختبارات | نجاح الاختبارات الجديدة والقديمة ذات الصلة |
| الأمان | صلاحيات، حقن تعليمات، PII، ومخرجات غير آمنة مغطاة |
| البيانات | migration قابلة للعكس، ولا أسرار أو بيانات حقيقية في Fixtures |
| الذكاء | Schema، مصدر، ثقة، fallback، ومراجعة مسجلة |
| التشغيل | retry idempotent، trace ID، ومؤشر فشل قابل للرصد |
| الرجوع | Feature Flag أو خطة rollback موثقة |

## ترتيب التنفيذ المقترح

1. خط أساس واختبارات حماية قبل التعديل.
2. P0: حالات المصدر والـFallback والمراجعة.
3. P1: Gateway وSchema وPrompt Registry والتتبع.
4. P4 المبكر: مجموعة تقييم ووظائف تحقق قبل RAG.
5. P2: RAG محدود لمسارات التكييف واللوائح والعقد.
6. P3: صندوق المراجعة وتغذية أسباب الرفض.
7. P5: أمن وخصوصية واختبارات Red Team.
8. P6: التوجيه والكلفة والـSLOs ثم التوسع تدريجياً.

## صيغة التقرير بعد كل مرحلة

اكتب تقريراً يتضمن: الملفات التي تغيرت، سبب كل تغيير، الوظائف المتأثرة، الاختبارات المشغلة ونتائجها، أي تحذيرات، مقارنة مؤشرات ما قبل/بعد، خطة rollback، والأسئلة التي تحتاج قرار مالك المنتج. لا تعتبر المرحلة مكتملة بوجود كود فقط؛ تكتمل عند نجاح الاختبارات والقياس والمراجعة البشرية.
