# خارطة طريق تطوير الذكاء الاصطناعي

## الأولوية المبدئية

لا يبدأ المشروع بإضافة وكلاء أكثر أو نماذج أغلى. البداية الصحيحة هي جعل المخرج الحالي قابلاً للثقة: معرفة مصدره، منع وصوله إلى قرار حساس بلا مراجعة، وقياس جودته. بعد ذلك فقط توسع قاعدة المعرفة والوكلاء.

| الترتيب | المرحلة | الغاية | بوابة الانتقال |
| --- | --- | --- | --- |
| 0 | تثبيت السلامة والوضوح | منع الخلط بين AI الحقيقي والاحتياطي | كل نتيجة تحمل حالة منشأ واضحة ولا توجد عملية حساسة تتم تلقائياً |
| 1 | بوابة AI موحدة | توحيد الاستدعاء والتحقق والرصد | جميع استدعاءات الذكاء تمر عبر واجهة واحدة مسجلة |
| 2 | جودة السياق والمعرفة | إجابات قانونية مستندة إلى مصادر معتمدة | RAG محدود النطاق مع استشهادات داخلية ومراجعة قانونية |
| 3 | التقييم قبل التوسع | قياس الجودة وإيقاف التراجع | مجموعة حالات معيارية ومؤشرات لكل وظيفة وقياس عند كل إصدار |
| 4 | تجربة المراجعة البشرية | جعل الاعتماد البشري سريعاً وقابلاً للتدقيق | صندوق مراجعة واضح وقرار قبول/رفض وسبب للتعديل |
| 5 | التحسين الاقتصادي والتوسع | اختيار النماذج حسب المهمة والتكلفة | توجيه نموذج وميزانية ومراقبة إنتاجية فعالة |

## المرحلة 0: السلامة وصحة الحالة

### الأعمال

- إضافة كيان موحد لحالة أي مخرج ذكي: `source` و`status` و`confidence` و`model_version` و`prompt_version` و`review_state` و`failure_reason`.

- فصل حالات `ai_success` و`fallback` و`manual_required` و`human_approved` في الواجهة والـAPI، وعدم استخدام علامة مثل `ai_done` عندما عاد النظام لقالب حتمي.

- جعل الإحالة التلقائية، ووسم المستند بأنه مرتبط، وإنشاء المهام من القرارات، وتقديم الرأي للعميل إجراءات ذات حدود ثقة وعناصر مراجعة.

- استبدال القوالب القانونية العامة بحالة واضحة: «تعذر التحليل الآلي — يلزم مراجعة»، مع عرض سبب قابل للفهم للطاقم.

- إيقاف إدخال أي مادة نظامية أو رقم أو سابقة قضائية من المخرج النهائي ما لم يربطها النظام بمصدر موثق في قاعدة المعرفة.

### معايير القبول

| المقياس | الهدف الأولي |
| --- | --- |
| النتائج التي يمكن معرفة مصدرها وحالتها | 100% |
| نتائج fallback المعروضة كنجاح AI | 0% |
| عمليات حساسة تنفذ من نتيجة AI بلا تأكيد إنسان | 0% |
| نتائج قانونية تحتوي ادعاءً نظامياً بلا مصدر أو علامة «يتطلب تحقق» | 0% في مخرجات المحامي المعتمدة |

## المرحلة 1: بوابة AI وطبقة التحقق

### الأعمال

- إنشاء `AI Gateway` خادمي موحد بدلاً من وجود منطق اختيار المزود والتحليل داخل خدمة عملاقة واحدة.

- تعريف عقود إدخال وإخراج لكل وظيفة: `TicketTriageResult`, `DocumentAnalysisResult`, `ConsultAnalysisResult`, `LegalDraftResult`, `MeetingDecisionResult`.

- استخدام JSON Schema صارم، مع حظر الحقول غير المتوقعة والتحقق البرمجي من الحدود والقيم والقوائم قبل حفظ النتائج.

- فصل `Prompt Registry` ذي الإصدارات عن منطق التطبيق؛ كل Prompt يحمل معرف إصدار ومراجعة ومالك ونطاق استخدام.

- إضافة معرف تتبع لكل طلب، وسجل منظم للطلب والنتيجة دون حفظ المحتوى الحساس كاملاً في السجل التشغيلي.

- توحيد سياسة المهلات وإعادة المحاولة وقاطع الدائرة وخطة fallback، مع فصل المهام المتزامنة للمحامي عن المهام المؤجلة للمعالجة الثقيلة.

### معايير القبول

| المقياس | الهدف الأولي |
| --- | --- |
| الاستدعاءات التي تمر عبر البوابة الموحدة | 100% |
| المخرجات المنظمة التي تتجاوز التحقق قبل التخزين | 100% |
| مخرجات JSON غير صالحة تصل لقاعدة البيانات | 0% |
| الاستدعاءات المتزامنة الثقيلة في عمليات الواجهة | 0 للوثائق والملخصات الكبيرة |
| سجلات تحتوي بيانات هوية أو نصوص مستندات كاملة دون سياسة صريحة | 0 |

## المرحلة 2: إدارة السياق والبحث القانوني الموثق

### الأعمال

- إنشاء سجل مصادر قانونية معتمدة من فريق المكتب: النظام، المادة، اللائحة، تاريخ السريان، المصدر، الولاية، المجال، ونسخة الوثيقة.

- بناء فهرس استرجاع محدود البداية لثلاثة مسارات فقط: التكييف، مسودات اللوائح، وتحليل العقد. لا ينقل إلى بقية المسارات قبل التقييم.

- تطبيق فلتر الاسترجاع قبل النموذج: الاختصاص السعودي، تاريخ السريان، نوع النزاع، ودرجة موثوقية المصدر.

- إجبار مخرجات الصياغة القانونية على إرفاق مصفوفة «ادعاء ← مصدر ← مقطع» داخلية للمحامي، وتحديد الجمل غير المدعومة بعلامة واضحة.

- بناء `Context Builder` يختار أقل قدر من بيانات الملف، وينقي HTML والتعليمات داخل مستندات العميل، ويحجب معرفات الهوية والجوال عند عدم الحاجة.

### معايير القبول

| المقياس | الهدف الأولي |
| --- | --- |
| مسودات التكييف/اللوائح التي تحمل مراجع قابلة للتحقق | ≥ 95% من الحالات التي تتطلب مراجع |
| مراجع غير متسقة مع نوع النزاع أو تاريخ السريان في عينة مراجعة | < 2% |
| الاسترجاع غير ذي الصلة في مجموعة تقييم محامين | < 10% |
| أقلية البيانات المرسلة للمزود الخارجي | يثبتها سجل حقول لكل مهمة |

## المرحلة 3: التقييم والاعتماد على البيانات

### الأعمال

- إنشاء مجموعة تقييم داخلية مجهلة الهوية، مقسمة حسب الوظيفة: فرز التذكرة، تحليل المستند، تلخيص الملف، تحليل الاستشارة، استخراج القرارات، وصياغة المذكرات.

- لكل حالة: مدخل مضبوط، نتيجة متوقعة أو Rubric محامي، مستوى صعوبة، نوع خطأ، ومراجع حقيقية عند الاقتضاء.

- تضمين حالات متعارضة وناقصة وحالات عربية عامية وفصحى ونصوص طويلة ومستندات خاطئة وحالات حقن تعليمات.

- إضافة تقييمات آلية للحقل المنظم، ثم مراجعة محام لعينة عمياء دورية ومقارنة مخرجات النسخة الجديدة بالنسخة الحالية.

- ربط قبول أي نموذج أو Prompt جديد بحد أدنى من الجودة وعدم حدوث تراجع في فئات المخاطر العالية.

### معايير القبول

| الوظيفة | مؤشر رئيسي | هدف أولي للانتقال |
| --- | --- | --- |
| فرز التذكرة | دقة القسم/النية مقابل الحقيقة المعتمدة | ≥ 90% |
| تحليل المستند | دقة النوع والارتباط | ≥ 90% |
| الملخص القانوني | اكتمال الحقائق وعدم إضافة وقائع | ≥ 95% اجتياز في مراجعة المحامي |
| الاستشهاد القانوني | صحة الارتباط بالمصدر | ≥ 95% |
| استخراج القرارات | الدقة وعدم خلق مهمة غير مذكورة | ≥ 98% لاختبار عدم الاختلاق |
| حماية حقن التعليمات | رفض أو عزل المحاولات العدائية | 100% في المجموعة المعيارية |

## المرحلة 4: المراجعة البشرية وتجربة المحامي

### الأعمال

- إنشاء «صندوق مراجعة AI» موحد يوضح: المخرج، المصدر، الأدلة/المقاطع، درجة الثقة، سبب التصعيد، والفرق بين النسخة الأصلية والمعدلة.

- تمكين المحامي من قبول الكل أو جزء محدد، تعديل فقرة، رفض مع تصنيف سبب، وإرسال النتيجة للتعلم التقييمي دون استخدام تلقائي لتدريب خارجي.

- إنشاء قواعد تصعيد واضحة: الثقة المنخفضة، تضارب المستندات، نقص دليل، ذكر مادة بلا مصدر، قيمة مطالبة عالية، أو محتوى شديد الحساسية.

- تحويل القرارات إلى «مهام مقترحة» أولاً، ثم إنشاء `Task` بعد اعتماد المستخدم؛ ويستثنى الإنشاء التلقائي إلا في حالات منخفضة المخاطر مصادق عليها بسياسة محددة.

- إظهار اسم ودور الذكاء الاصطناعي للمستخدم  كموظف بشري .

### معايير القبول

| المقياس | الهدف الأولي |
| --- | --- |
| مخرجات المخاطر العالية التي راجعها محامٍ قبل الإرسال/الاعتماد | 100% |
| زمن مراجعة المسودة النموذجي | ينخفض ≥ 30% مقارنة بالصياغة اليدوية المرجعية |
| المخرجات المرفوضة مع سبب منظم | ≥ 90% من حالات الرفض |
| مهام منشأة من AI دون حالة اعتماد مناسبة | 0 |

## المرحلة 5: الخصوصية والأمن والاستمرارية

### الأعمال

- تصنيف بيانات الذكاء الاصطناعي إلى: عامة، داخلية، سرية، وبيانات شديدة الحساسية، مع سياسة تسليم مختلفة لكل فئة.

- تطبيق فحص PII وتمويه البيانات، وتشفير الملفات والسجلات الحساسة، وسياسة احتفاظ ومحو، وسجل وصول للمراجعات والمصادر.

- إضافة حواجز Prompt Injection قبل وبعد الاسترجاع؛ تعامل كل نص في مستند أو رسالة كبيانات لا كتعليمات.

- تطبيق مبدأ أقل صلاحية: الوكيل لا يملك وصولاً مباشراً إلى قاعدة البيانات أو الدفع أو البريد أو Zoom، بل أدوات ضيقة ومصرح بها فقط.

- إجراء اختبارات red-team دورية مع حالات تسريب وإفصاح وحقن واستدعاء عملية حساسة، وربط أي فشل بخطة تصحيح وإعادة اختبار.

### معايير القبول

| المقياس | الهدف الأولي |
| --- | --- |
| نجاح سيناريوهات حقن التعليمات في تغيير سلوك النظام | 0 في الاختبارات المعيارية |
| تسريب بيانات ملف غير مصرح به في الاختبارات | 0 |
| أدوات ذات صلاحيات تنفيذية يملكها نموذج اللغة مباشرة | 0 |
| طلبات حساسة تمر ببوابة تصعيد ومراجعة | 100% |

## المرحلة 6: اختيار النماذج والكلفة والملاحظة التشغيلية

### الأعمال

- إنشاء سجل قدرات للنماذج بالاعتماد على اختبار فعلي، لا على الاسم فقط: الدقة العربية، JSON، السياق الطويل، PDF/صور، السرعة، والكلفة.

- استخدام توجيه نماذج حسب نوع المهمة: سريع للفرز، متعدد الوسائط للوثائق، أقوى لصياغة المسودات بعد RAG، ونموذج حكم مستقل للتقييم.

- اعتماد نهج «الرخيص أولاً ثم التصعيد» للمهام القابلة للقياس؛ يعاد تشغيل الحالات منخفضة الثقة أو الفاشلة فقط بنموذج أقوى.

- لوحات تشغيل تعرض مستوى الجودة، إعادة المحاولات، نسبة fallback، زمن الاستجابة، كلفة المهمة، واستهلاك المستخدم أو القسم.

- وضع ميزانيات وquotas وتنبيهات عند تغير الكلفة أو نسبة الأخطاء أو زمن المعالجة بشكل غير طبيعي.

### معايير القبول

| المقياس | الهدف الأولي |
| --- | --- |
| الرؤية التشغيلية لكل طلب (مهمة/نموذج/زمن/نتيجة/كلفة) | 100% |
| ارتفاع مفاجئ في الفشل أو الكلفة يظهر بتنبيه | ضمن دورة مراقبة واحدة |
| تراجع الجودة عند تغيير نموذج/Prompt يصل للإنتاج | 0 دون اجتياز التقييم |
| إنفاق المهام القابلة للفرز يتجاوز ميزانية القسم | 0 دون تنبيه أو إيقاف |

## تسلسل الإصدار

1. إصدار داخلي فقط للموظفين مع تسجيل ومراجعة ولا تغيير تلقائي في الحالات الحساسة.

1. إصدار محدود لحالات تذاكر منخفضة المخاطر، مع وضع «اقتراح فقط» ومقارنة صامتة مع التنفيذ القائم.

1. تفعيل مسارات منفردة بعد تجاوز معيارها، وليس تفعيل المنظومة كاملة دفعة واحدة.

1. تحسين Prompt أو النموذج من خلال نتائج التقييم؛ لا تنفذ Fine-tuning قبل أن تثبت البيانات المعيارية أن المشكلة نمط متكرر لا يحل بالسياق أو النظام أو الـRAG.

1. بعد استقرار مؤشرات الجودة والحوكمة، توسع إلى تنفيذات أكثر حساسية مع مراجعة إلزامية مستمرة.

## اجتماع حوكمة قصير ومتكرر

يقام اجتماع عملي دوري يضم مالك المنتج، محامياً مسؤولاً، ممثلاً للأمن/الخصوصية، ومسؤولاً تقنياً. يراجع الاجتماع: العينات المرفوضة، الأخطاء عالية الخطورة، مصادر المعرفة المضافة، تغييرات Prompt والنموذج، الكلفة، ونسب مراجعة البشر. القرار المطلوب في كل اجتماع هو قبول/إيقاف/تعديل وظيفة بعينها، لا تقييم عام انطباعي للذكاء الاصطناعي.

## قرارات لا تؤجل

1. عدم اعتبار مخرجات AI قانوناً أو فتوى أو قراراً نهائياً.

1. عدم تقديم المخرج الاحتياطي كنجاح AI.

1. عدم تخزين أو إرسال بيانات أكثر مما تحتاجه المهمة.

1. عدم السماح للنموذج بتنفيذ فعل خارجي أو حساس مباشرة.

1. عدم ترقية نموذج أو Prompt بلا مجموعة تقييم ومراجعة محام.

1. عدم بناء منظومة متعددة الوكلاء قبل أن تثبت القياسات أن الوكيل الواحد المحدود لا يكفي.
