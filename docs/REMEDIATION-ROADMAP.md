## 1. الملخص التنفيذي

### 1.1 الهدف

ترقية المنصة من معمارية **عميل ذكاء اصطناعي واحد مركزي** (`LegalAiService`، 841 سطراً، 13+ مسؤولية) إلى **معمارية ذكاء اصطناعي للإنتاج قابلة للتوسع ومتعددة الوكلاء** — **دون كسر النظام الحالي** ودون إعادة كتابة شاملة.

### 1.2 النطاق (In Scope)

- تفكيك `LegalAiService` إلى بوابة LLM + وكلاء متخصصين + أدوات + خدمات خلفية.
- إضافة القدرات الحرجة المفقودة: tool calling، RAG/قاعدة معرفة، ذاكرة طويلة المدى، OCR محلي، إثبات منشأ AI.
- تأسيس Ops حقيقي: طوابير Jobs، Docker، Supervisor، CD pipeline، رصد.
- توسيع تغطية الاختبارات لتشمل مسارات الذكاء الاصطناعي و realtime.

### 1.3 خارج النطاق (Out of Scope)

- إعادة تصميم واجهات المستخدم (UI) أو هوية المنتج.
- تغيير المخطط العلائقي (schema) الأساسي للكيانات (التذاكر/القضايا/التنفيذ) إلا بإضافات غير مدمِّرة.
- استبدال مزوّدي الـ LLM الحاليين (GLM/Claude/Gemini) — نحتفظ بهم عبر البوابة.

### 1.4 معايير النجاح (Success Criteria)

| المعيار | الهدف القابل للقياس |
|---|---|
| زمن استجابة الـ AI للعميل | < 2 ثانية للاستقبال الأول (P95) |
| توافر مسار الـ AI | > 99.5% (بفضل اعتماد المزود + إعادة المحاولة) |
| تغطية الاختبارات لمسارات الـ AI | > 80% (حالياً ~0%) |
| وحدة المنطق (Single Responsibility) | لا خدمة واحدة تتجاوز مسؤولية واحدة قابلة للتعبير |
| رصد التكلفة | كل مخرَج AI يحمل تكلفته + المزود + النموذج |
| زمن عامل FPM المحجوز | عمليات الـ AI الثقيلة كلها على طوابير، لا على request thread |

### 1.5 الحقائق الهندسية المؤكَّدة (نقطة الانطلاق)

> هذه ليست افتراضات — مؤكَّدة من الكود والتهيئة.

- ✅ **مجموعة اختبارات حقيقية موجودة**: 167 اختباراً في 27 ملفاً (`tests/Feature/`) + Pest 4. نبني عليها.
- ✅ **CI موجود**: GitHub Actions (اختبارات + Pint + PHPStan + ESLint). لكن **بلا CD**.
- ❌ **بلا Docker / Supervisor / deploy scripts** — Ops غير مؤسَّس.
- ❌ **بلا rate limiting على الـ AI** + **تسريب أسرار محتمل** (`.env` مُتتبَّع في working tree بمفاتيح حية).
- ❌ **مسارات الـ AI و realtime غير مغطاة اختبارياً** (المفاتيح مُصفّرة في `phpunit.xml`).
- ❌ **بلا اختبارات Frontend** (`package.json` بلا `test`/Vitest رغم ذكرها في `DEVELOPER_GUIDE.md` — قسم عالق/stale).
- ⚙️ التهيئة الإنتاجية: `CACHE_STORE=database`، `QUEUE_CONNECTION=database`، `BROADCAST_CONNECTION=reverb`.

## 2. المبادئ الحاكمة

> كل قرار تصميمي خلال المشروع يُختبَر ضد هذه المبادئ.

| # | المبدأ | المعنى العملي |
|---|---|---|
| **P1** | **ترحيل تدريجي، لا big-bang** | كل مرحلة قابلة للنشر مستقلة وتُسلَّم منفصلة. لا تجميع سنتين من التغييرات. |
| **P2** | **لا كسر النظام** | `app(LegalAiService::class)` يبقى يعمل طوال الانتقال. الواجهة (facade) تُحافظ على التوافق العكسي حتى يكتمل الترحيل. |
| **P3** | **إعادة استخدام أقصى** | منطق المزود الحالي (`run`/`viaGlm`/`viaAnthropic`/`viaGemini`) يُنتقل كما هو إلى `LlmGateway`، لا يُعاد كتابته. القوالب الاحتياطية (fallbacks) تُحتفظ. |
| **P4** | **Feature Flags لكل تغيير** | كل قدرة جديدة محمية بمفتاح تهيئة (مثل `AI_TICKET_AGENT`). التفعيل التدريجي: dev → staging → canary → prod. |
| **P5** | **اختبار أولاً (Test-first للسلوك الجديد)** | كل وكيلاً/أداة جديدة لها اختبارات (mock للمزوّد) قبل الدمج. التعديلات على الموجود لها اختبارات حارسة (characterization tests) أولاً. |
| **P6** | **المسؤولية القانونية بشرية دائماً** | أي رأي/مسودة/نتيجة تُرسَل للعميل تتطلب اعتماداً بشرياً. الـ AI يُوصي/يُساعد، لا يُقرِّر قانونياً. |
| **P7** | **الرصدية افتراضية (Observability-first)** | كل مخرَج AI يحمل: المزود، النموذج، إصدار الـ prompt، الحالة (ok/fallback)، التكلفة، الزمن. |
| **P8** | **عكس المُفعَّل افتراضياً (Secure defaults)** | القدرات الجديدة تُفتَح بـ flag = false للإنتاج حتى تُختبر. الـ AI kill-switch يبقى متاحاً. |

### M2 — بوابة LLM (LlmGateway) + caching

**منهج التنشيط**: dev → staging (تشغيل تلقائي) → prod **off افتراضياً** (P8) → canary (نسبة حركة) → 100%.

### 8.3 النشر والتراجع

- [ ] **T-D01** CD pipeline: build → test → `vite build` → deploy staging. يدوي إلى prod.
- [ ] **T-D02** **Blue-green / canary** للإنتاج: نسبة حركة صغيرة للنسخة الجديدة قبل الكامل.
- [ ] **T-D03** **Rollback فوري**: إطفاء كل flags الجديدة ← العودة للنظام القديم. (T-808 يؤسسه.)
- [ ] **T-D04** **Database migrations آمنة**: كل migration **non-destructive** (إضافة أعمدة `ai_meta` قابلة للقيم null)؛ لا حذف/إعادة تسمية أثناء الترحيل.
- [ ] **T-D05** نسخ احتياطي قبل كل نشر prod + خطة استعادة مُختبَرة.

### 8.4 المراقبة (Observability)

- [ ] **T-D06** مقاييس تطبيقية: Laravel Pulse/Telemetry (موجود partial) — طوابير، بطء، أخطاء.
- [ ] **T-D07** مقاييس AI (من M1): التكلفة، الزمن، نسبة fallback لكل مزوّد/وكيل.
- [ ] **T-D08** تنبيهات: تعطل مزوّد LLM، ارتفاع fallback، تجاوز سقف تكلفة يومي، امتلاء الطوابير.
- [ ] **T-D09** healthcheck لكل خدمة (app/worker/reverb/db).

## 10. معايير القبول النهائية (Project Definition of Done)

> لا يُعلَن المشروع منجزاً حتى تتحقق **كل** النقاط.

### 10.1 معمارية

- [ ] `LegalAiService` لم يعد عميلاً ضخماً — أصبح facade رقيقاً (أو مُستبعَداً) وكل مسؤولية في مكوّن مستقل (وكيل/أداة/خدمة).
- [ ] بوابة `LlmGateway` معزولة عن منطق الأعمال ومغطاة باختبارات.
- [ ] لا عمل AI ثقيل في request thread (كلها طوابير).
- [ ] tool calling أصلي بديل regex JSON.

### 10.2 القدرات

- [ ] RAG + قاعدة معرفة فعّالة وقابلة للقياس.
- [ ] ذاكرة طويلة المدى + تلخيص الأقدم.
- [ ] OCR محلي موثوق.
- [ ] إثبات منشأ AI كامل على كل مخرَج.

### 10.3 الجودة

- [ ] ≥ 80% تغطية للكود الجديد + golden tests لكل وكيل.
- [ ] اختبارات Frontend (Vitest) مفعَّلة.
- [ ] اختبارات E2E (Playwright) لرحلات العملاء.
- [ ] CI أخضر باستمرار؛ PHPStan level 7 نظيف.

### 10.4 العمليات

- [ ] Docker + Supervisor + CD pipeline فعّالة.
- [ ] لوحة رصد وكلاء تعرض مقاييس حيّة.
- [ ] سقف تكلفة يومي + تنبيهات + rollback مُختبَر.

- [ ] لا أسرار في git + تدوير موثَّق.
- [ ] PII redaction قبل كل استدعاء مزوّد.
