## 1. الميثاق الهندسي والضوابط التنفيذية الصارمة لوكلاء الذكاء الاصطناعي

يُعد هذا الملف العقد الدستوري الأعلى للمشروع. يلتزم أي وكيل ذكاء اصطناعي (مثل Claude AI أو Gemini AI) أو مطور برمجيات بالامتثال التام للضوابط التالية قبل الشروع في كتابة أو تعديل أي سطر برمجي:

### 1.1 بروتوكول الفحص المسبق قبل كتابة الكود (Check-Before-Code Protocol)
* **القاعدة:** يُحظر تماماً توليد أي كود برمجي جديد (Class, DTO, Repository, Service, Transition, Controller, Component) بناءً على التخمين أو الذاكرة المجردة.
* **إجراء الفحص الإلزامي:**
  1. قراءة شجرة المجلدات ذات الصلة في `app/Domain/` و `resources/js/`.
  2. البحث عن الكائنات القائمة المشابهة للتحقق من عدم وجود تنفيذ مسبق أو كائن يؤدي الغرض لمنع التكرار (Zero Duplication).
  3. فحص أسماء الحقول في المهاجرات (Migrations) والنماذج (Models) ومطابقتها حرفياً مع الكود الجديد.
  4. التحقق من التزام الكود بأنماط الـ DDD المعتمدة في هذا الدليل.

### 1.2 سجل قرارات المعمارية المعتمدة (ADR Compliance)
* **القاعدة:** أي وكيل ذكاء اصطناعي مُلزم بقرارات ADR المعتمدة في هذا الدليل (انظر القسم 2).
* **الحظر:** يُمنع منعاً باتاً استبدال الأنماط الهندسية (مثل إلغاء نمط الانتقالات لصالح التعديل المباشر، أو استبدال Inertia بـ SPA منفصل، أو دمج استعلامات الـ DB داخل المتحكمات) دون فتح قرار ADR رسمي واعتماده مسبقاً.

### 1.3 استقلال طبقة الدومين الصرفة (Pure Domain Layer Invariant)
* **القاعدة:** طبقة النطاق (`Domain Layer`) يجب أن تكون نقية وخالية تماماً من أي ارتباط بإطار العمل (Framework Agnostic).
* **الالتزامات الصارمة:**
  * **كيانات النطاق الصرفة (Pure Domain Entities):** تُبنى بلغة PHP الصرفة دون وراثة كلاسات إطار العمل (`Illuminate\Database\Eloquent\Model`). مثال: كائن الدومين `TicketEntity`.
  * **كائنات القيمة (Value Objects):** كائنات غير قابلة للتغيير (Immutable) تمثل مفاهيم الدومين بلغة PHP نقية، مثل (`TicketNumber`, `TicketType`, `ClosureReason`).
  * **عزل الوصول للبيانات (Repository Interfaces):** واجهات المستودعات تُعرّف حصراً داخل طبقة الدومين (`TicketRepositoryInterface`)، ويتم تطبيقها فعلياً في طبقة البنية التحتية (`Infrastructure Layer`) عبر محولات Eloquent.
  * منع تسريب أي دوال تابعة لإطار العمل أو الـ HTTP (`Request`, `Session`, `Cookie`, `Response`) داخل طبقة الدومين.

### 1.4 لغة المنطق والتخزين: الإنجليزية الصارمة vs العربية للعرض فقط (Language Governance)
* **القاعدة الذهبية:**
  * **المنطق والتخزين (Logic & Storage):** باللغة الإنجليزية حتماً وبشكل قطعي (`snake_case` للبيانات و `PascalCase` للأصناف والـ Enums).
  * **العرض والواجهات (Localized Views):** باللغة العربية عبر قواميس الترجمة وتسميات الـ Enum المخصصة.
* **التفصيل الإلزامي:**
  1. **مفاتيح الحالات (States):** تُكتب وتُخزن في قاعدة البيانات كـ English Enums (مثال: `TicketStatus::AwaitingDocs = 'awaiting_docs'`, `CaseStatus::InCourt = 'in_court'`).
  2. **الأدوار (Roles):** تُخزن بالإنجليزية (`client`, `employee`, `lawyer`, `admin`).
  3. **الصلاحيات (Permissions):** تُصمم وتُخزن بصيغة أسماء بالإنجليزية النظيفة (`tickets.manage`, `cases.record_ruling`, `consults.approve_summary`, `invoices.settle`).
  4. **حظر الفحص باللغة العربية في الواجهة الأمامية (Strict Frontend Constraint):**
     * ❌ **يُمنع قطعياً:** كتابة أي شرط منطقي في React/Vue/Inertia يفحص نصوصاً عربية، مثل:
       ```typescript
       // ❌ كود محظور ومرفوض رفضاً باتاً
       if (ticket.status === 'مكتملة') { ... }
       if (item.stage_label === 'قيد الانتظار') { ... }
       ```
     * ✅ **الكود المعتمد:** الفحص يتم دائماً عبر مصفوفة الإجراءات القادمة من السيرفر أو عبر مفتاح الحالة الإنجليزي الثابت:
       ```typescript
       // ✅ الكود المعتمد هندسياً
       if (ticket.actions.can_convert_case) { ... }
       if (ticket.status === TicketStatus.ReadyForOutcome) { ... }
       ```
  5. **الترجمة العربية:** تنحصر النصوص العربية في دوال العرض في الـ Backend مثل `clientLabel()` أو ملفات الترجمة `lang/ar/*.php` ومكونات العرض في الواجهة الأمامية.

### 1.5 إنفاذ شجرة الصلاحيات والأدوار في طبقة الـ Backend (RBAC & ABAC Enforcements)
* **القاعدة:** واجهة المستخدم هي مرآة عرض فقط (Presentation Mirror). إخفاء أو تعطيل الزر في الواجهة لا يُعتبر حماية أمنية بأي شكل من الأشكال.
* **الإلزام:** كل عملية انتقال حالة، أو إنشاء سجل، أو استعراض مستند قانوني حساس، يجب أن تخضع لفحص صارم في الـ Backend:
  1. التحقق من الدور والصلاحية النظامية (RBAC).
  2. التحقق من السياق وملكية السجل (ABAC - مثال: هل المحامي مسند لهذه القضية؟ هل التذكرة مملوكة لهذا العميل؟).
  3. التحقق من جاهزية الحالة والمسار داخل حارس الانتقال (`Transition Guard`).

### 1.6 بروتوكول استلام وتسليم الوكلاء وسجل الحالة (Multi-Agent Handover Protocol)
* **القاعدة:** عند انتقال العمل بين وكلاء ذكاء اصطناعي مختلفين (Claude AI, Gemini, Cursor, Copilot):
  1. **الاستلام:** يلتزم الوكيل بمطالعة ملفات الحوكمة [`AGENTS.md`](file:///AGENTS.md) أو [`CLAUDE.md`](file:///CLAUDE.md) وسجل الحالة الحي [`PROJECT_STATUS.md`](file:///PROJECT_STATUS.md) فوراً قبل كتابة الكود لمعرفة ما تم إنجازه والمهمة التالية المحددة له.
  2. **التنفيذ:** الالتزام الصارم بقواعد الـ DDD الصافي وأنماط هذا الدليل مع تشغيل الاختبارات الآلية (`php artisan test` و `npx tsc --noEmit`).
  3. **التسليم والتوثيق:** بعد إتمام أي مهمة وقبل إنهاء الجلسة، يُلزم الوكيل بتحديث جدول **سجل تسليم الوكلاء (Agent Handover Log)** في [`PROJECT_STATUS.md`](file:///PROJECT_STATUS.md) لتوثيق الملفات المعدلة، نتائج الاختبارات، وتحديد الخطوة التالية بدقة للوكيل الذي يليه.

### 1.7 حظر ازدواجية الإجراءات ومسارات الالتفاف (Single Source of Truth & Zero Bypass Invariant)
* **القاعدة:** يُحظر تماماً وجود مسارات التفاف (Bypass / Shortcuts) تتيح تنفيذ قرار أو تحويل حالة دون المرور بدورة الحوكمة الرسمية المعتمدة في النظام.
* **الالتزامات الصارمة:**
  1. **حوكمة المسارات الأربعة:** تقرير مآل التذكرة (طلب استشارة، تحويل لقضية، تحويل لتنفيذ، إلغاء مسبب) يتم حصراً عبر مكون واجهة واحد هو بطاقة حوكمة المسارات (`TicketTrackDecisionCard`)، ومسار انتقال معتمد واحد في الباك إند هو `ApproveOutcomeTrack`.
  2. **حظر تكرار الأزرار:** يُمنع تكرار أي زر أو إجراء فرعي في لوحات خيارات إضافية (مثل أزرار التحويل المباشر في `TicketActionsPanel`).
  3. **توحيد الـ API والواجهة:** كل وظيفة تجارية لها مسار API واحد خاضع لنفس الصلاحيات وقواعد التحقق، ومتحكم واحد، ومكون واجهة مستخدم وحيد؛ منعاً لتضخم الكود وتشتت الصيانة وضماناً لنقاء معمارية الـ DDD.

### 1.8 ضوابط التنفيذ وخط الأساس قبل بدء أي مرحلة أو عملية (Pre-Execution Baseline & Scope Controls)
* **عزل الفروع ونقاط الرجوع:** ينبغي تنفيذ كل مرحلة على فرع مستقل باسم واضح، مع حفظ نقطة رجوع قبل بداية المرحلة. لا يجوز جمع إصلاحات P0 مع إعادة هيكلة واسعة في Commit واحد، لأن ذلك يصعب معرفة سبب أي انحراف.
* **تسجيل خط الأساس (Baseline) الإلزامي قبل البدء:**
  1. نتيجة فحص TypeScript (`npx tsc --noEmit`).
  2. نتيجة اختبارات نطاق المعين (`php artisan test --filter=<DomainName>`).
  3. قائمة مسارات HTTP الحالية المرتبطة بالنطاق.
  4. قائمة الحالات من الخادم والواجهة.
  5. حالة قاعدة البيانات المستخدمة في الاختبارات.
  6. قائمة الملفات التي ستتأثر بالمرحلة.
* **التحقق الشامل بعد كل مرحلة:** بعد كل مرحلة يجب تشغيل الاختبارات المرتبطة بها، ثم تشغيل اختبارات النطاق كاملة. لا تعتبر المرحلة مكتملة بمجرد نجاح اختبار واحد؛ يجب تحقق معايير القبول المحددة في هذه الوثيقة (نجاح 100% وخلو تام من أخطاء الأنواع).

## 2. سجل القرارات المعمارية المعتمدة (ADR Logs)

| رقم القرار | العنوان المعماري | القرار المعتمد | العلة والأثر الهندسي |
| :--- | :--- | :--- | :--- |
| **ADR-001** | إدارة دورة حياة الكيانات | حظر التعديل المباشر للحالات واعتماد محرك الانتقالات `Workflow::run()` | منع تشتت تعديل الحالات عبر المتحكمات، وضمان تسجيل التدقيق في `journey_transitions` وإطلاق الأحداث المرافقة بصورة ذرية. |
| **ADR-002** | المعمارية التقريرية للواجهة | اعتماد `Server-Driven Actions Matrix` | منع تسريب منطق الأعمال (Business Logic) إلى مكونات React؛ الخادم يعيد مصفوفة `actions` صريحة تحدد المسموح والممنوع لكل مستخدم. |
| **ADR-003** | إدارة المعاملات المزدوجة | القفل التشاؤمي الإلزامي `lockForUpdate()` عند تنفيذ الانتقالات | حماية النظام من Race Conditions، ومنع تكرار إنشاء القضايا أو ملفات التنفيذ أو السداد المزدوج. |
| **ADR-004** | لغة المنطق وقواعد البيانات | توحيد مفاتيح الحالات والصلاحيات باللغة الإنجليزية، واقتصار العربية على طبقة العرض | إزالة الهشاشة البرمجية الناتجة عن مقارنة النصوص العربية (مشاكل الهمزات والترميز UTF-8)، وتحقيق معايير النظم البنكية والمؤسسية. |
| **ADR-005** | مرونة أعطال الذكاء الاصطناعي | العزل والتهدئة التدريجية (Graceful Degradation) والتصعيد البشري الفوري | حظر نقل التذكرة لـ `AwaitingDocs` عند عطل الـ AI، وتثبيتها في `Analyzing` مع تنبيه الاستقبال اليدوي لحفظ رضا العميل وسرية أخطاء النظام. |
| **ADR-006** | استقلالية طبقة الدومين الصرفة (Pure Domain) | فصل منطق النطاق عن Eloquent عبر كائنات نطاق صرفة (Pure Entities) ومستودعات مجردة | حماية منطق الأعمال من التبعيات الخارجية، وضمان نقاء القواعد التجارية وسهولة الاختبارات النمطية (Unit Tests) بنسبة 100% بلغة PHP دون تشغيل قاعدة البيانات. |
| **ADR-007** | تجميد السجلات المحولة | الإغلاق القطعي (`is_frozen = true`) للتذاكر المحولة لقضايا أو تنفيذ | منع التعديل على التذكرة بعد تفريخ الكيان الجديد؛ تظل التذكرة مرجعاً أرشيفياً تاريخياً للقراءة فقط. |
| **ADR-008** | استراتيجية ترحيل الكود القديم (Legacy Migration) | تطبيق نمط Strangler Fig والتعايش عبر محولات Repositories والتفويض التدريجي | منع الكسر الفجائي للنظام (Zero Downtime)، وضمان استمرار عمل المسارات واللوحات وقواعد البيانات القائمة دون أي انقطاع. |
| **ADR-009** | حظر مسارات الالتفاف وتوحيد قرارات المآل | إزالة كافة أزرار الالتفاف الإجرائي المباشر واعتماد حوكمة المسارات الأربعة حصراً (`TicketTrackDecisionCard` و `ApproveOutcomeTrack`) | القضاء على تشتت وتضخم الأكواد وتعدد الـ APIs لنفس الوظيفة، وضمان خضوع أي تحويل إلى استشارة أو قضية أو تنفيذ أو إغلاق للتسبيب النظامي واعتماد الإدارة والتسجيل التدقيقي الموحد. |

## 3. الهيكل المعماري للطبقات الأربع (Clean DDD 4-Tier Architecture)

يتبع النظام النمط المعماري الموجه بالنطاق المكون من أربع طبقات واضحة الحدود:

```
┌────────────────────────────────────────────────────────────────────────┐
│ 1. طبقة التقديم (Presentation Layer)                                  │
│    Controllers, Inertia Page Responses, Form Requests, View Models    │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2. طبقة التطبيق (Application Layer)                                   │
│    Application Services, DTOs, Commands, Queries, Use Cases            │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3. طبقة المجال الصرفة (Pure Domain Layer)                              │
│    Entities (TicketEntity), Value Objects, Domain Events, Interfaces   │
└──────────────────────────────────▲─────────────────────────────────────┘
                                   │
                                   │ (Dependency Inversion)
┌──────────────────────────────────┴─────────────────────────────────────┐
│ 4. طبقة البنية التحتية (Infrastructure Layer)                           │
│    Eloquent Repositories, DB Transactions, External APIs, PDF, AI      │
└────────────────────────────────────────────────────────────────────────┘
```

### 3.1 طبقة المجال الصرفة (Pure Domain Layer)
* **المسار:** `app/Domain/{SubDomain}/`
* **المحتويات:**
  * **Pure Entities:** كائنات تحتوي على الهوية والمنطق التجاري الصرف بلغة PHP نقية (مثل `TicketEntity`, `ConsultEntity`, `LegalCaseEntity`).
  * **Value Objects:** كائنات قيمة منضبطة غير قابلة للتغيير (مثل `TicketNumber`, `TicketType`, `ClosureReason`, `Money`).
  * **Enums:** الكتالوجات الصارمة للحالات والأدوار (مفاتيح وقيم إنجليزية).
  * **Domain Events:** أحداث تمثل ما وقع بالفعل داخل النطاق (`TicketTransmutedToCase`, `ConsultationPaid`).
  * **Repository Interfaces:** عقود حفظ واسترجاع البيانات المجردة (مثل `TicketRepositoryInterface`).

### 3.2 طبقة التطبيق (Application Layer)
* **المسار:** `app/Application/{SubDomain}/` أو `app/Services/{SubDomain}/`
* **المحتويات:**
  * **Application Services:** خدمات تنسيق السيناريوهات (مثل `TicketConsultationService`, `TicketConversionService`, `InvoiceSettlementService`).
  * **DTOs (Data Transfer Objects):** كائنات نقل البيانات بين المتحكمات والخدمات، منضبطة الأنواع وخالية من السلوك.
  * **Commands / Handlers:** أوامر تنفيذ العمليات (CQRS Light) لمنع تضخم الكود.

### 3.3 طبقة البنية التحتية (Infrastructure Layer)
* **المسار:** `app/Infrastructure/` و `app/Models/`
* **المحتويات:**
  * **Eloquent Models:** نماذج التخزين والربط مع قاعدة البيانات MySQL/PostgreSQL.
  * **Repositories Implementation:** تطبيق الـ Interfaces باستخدام Eloquent و Query Builder.
  * **External Services:** محولات الخدمات الخارجية (بوابات الدفع، بوابة ناجز، مزودي الذكاء الاصطناعي، Zoom API، SMS Gateways).
  * **Persistence Mappers:** تحويل Eloquent Models إلى Domain Entities والعكس.

### 3.4 طبقة التقديم (Presentation Layer)
* **المسار:** `app/Http/Controllers/` و `resources/js/`
* **المحتويات:**
  * **Thin Controllers:** استقبال الطلب، التحقق الأمني، استدعاء خدمة التطبيق، وتمرير مصفوفة البيانات ومصفوفة الإجراءات `actions`.
  * **React / Inertia Components:** واجهات المستخدم المعتمدة كلياً على البيانات المصدرة من الخادم.

#### القواعد المالية الصارمة:
1. **منع السداد على المسودات أو الملغاة:** تطبق الفواتير حارس `isPayable()` الصارم؛ حيث يُمنع منعاً باتاً استقبال أي دفعة على فاتورة مسودة أو ملغاة أو مسددة بالكامل.
2. **الحالة المشتقة اللحظية (`liveStatus`):** حالة الفاتورة "متأخرة" (`Overdue`) لا تُخزن كصف في قاعدة البيانات، بل تُشتق لحظياً عند القراءة إذا كان تاريخ الاستحقاق `due_date < now()` ولم تكن الفاتورة مدفوعة.
3. **التكامل مع السداد البنكي والإلكتروني:** تسجيل الدفعات يمر عبر خدمة `InvoiceSettlementService` مع دعم السداد الجزئي، وإرفاق إيصالات التحويل البنكي وتأكيدها بصلاحية المحاسبة.

## 5. محرك الانتقالات والتحولات بين النطاقات (Inter-Domain Transmutations & Workflow Engine)

تعتمد المنصة محرك انتقال موحد فائق الانضباط (`Workflow::run`) لكافة العمليات التي تغير حالات الكيانات.

### 5.1 معمارية كلاس الانتقال الموحد (`Transition<TModel>`)
يرث كل انتقال من `App\Domain\Journey\Transition` ويحدد بوضوح:
1. **العمود المستهدف (`column`):** الحقل المراد تغييره في الجدول (مثل `status`).
2. **الحالات المقبولة للانتقال (`accepts`):** قائمة الحالات المصدرية المسموح بالتحويل منها.
3. **حارس الصلاحية والفاعل (`deny`):** فحص صلاحية المستخدم الحالي بالنسبة للكيان (إرجاع `string` مسبب للرفض 403 أو `null` للسماح).
4. **حارس شروط العمل (`guard`):** فحص شروط البيانات والملفات والمدفوعات (إرجاع `string` مسبب للرفض 422 أو `null` للسماح).
5. **التنفيذ الفعلي (`apply`):** تطبيق التعديل على الحقول.
6. **سجل التدقيق (`record`):** صياغة السجل الذي يُكتب في `journey_transitions`.
7. **الأحداث المرافقة (`events`):** قائمة الأحداث اللحظية التي تُطلق بعد نجاح الالتزام المالي والتخزيني (`afterCommit`).

### 5.2 تسلسل التنفيذ في محرك `Workflow::run()`
```
[ بدء المعاملة DB Transaction ]
               │
               ▼
[ القفل التشاؤمي للصف: lockForUpdate() ]
               │
               ▼
[ فحص الحالة المصدرية: accepts($from) ] ── (فشل) ──► رمي TransitionDenied::state() [422]
               │
               ▼
[ فحص صلاحية الفاعل: deny($locked, $actor) ] ── (فشل) ──► رمي TransitionDenied::forbidden() [403]
               │
               ▼
[ فحص شروط العمل والبيانات: guard($locked, $payload) ] ── (فشل) ──► رمي TransitionDenied::invalid() [422]
               │
               ▼
[ تشغيل الحارس العام: StateWriteGuard::permit() ]
               │
               ▼
[ تطبيق التعديلات: transition->apply() ]
               │
               ▼
[ تسجيل خط الرحلة: JourneyTransition::create() ]
               │
               ▼
[ التزام المعاملة: DB Commit ]
               │
               ▼
[ إطلاق الأحداث اللحظية بعد الالتزام: Event::dispatch() ]
```

### 5.3 بروتوكول التحويل بين النطاقات (Inter-Domain Transmutations)
عند اتخاذ قرار تحويل تذكرة إلى قضية أو تنفيذ أو استشارة:
1. **التسلسل الذري (Atomic Execution):** إنشاء الكيان الجديد (قضية/تنفيذ) ونقل حالة التذكرة الأصلية وتجميدها يقعان داخل نفس الـ `DB::transaction`.
2. **تجميد السجل المصدر (Immutability Freeze):** يُضبط الحقل `is_frozen = true` على التذكرة الأصلية فور اكتمال التحويل، مما يمنع تشغيل أي انتقال مستقبلي عليها.
3. **حقن الروابط العميقة (Deep Linking):** يُخزن معرف الكيان الجديد في سجل الانتقال، وتوجه الواجهة المستخدم مباشرة إلى السجل الجديد (مثل `/cases/142`) وليس إلى شاشات الفهرس العامة.

}

## 7. مرونة الذكاء الاصطناعي وحماية الخدمة من الأعطال (AI Resilience & Graceful Degradation)

عند حدوث أي عطل أثناء تحليل المستندات أو استخراج البيانات آلياً عبر الذكاء الاصطناعي، يلتزم النظام بالمعايير التالية لمنع تعطل الرحلة القانونية:

### 7.1 تصنيف أعطال الذكاء الاصطناعي القياسية (`AiFailure`):
1. **أعطال المزود والاتصال (`PROVIDER_UNAVAILABLE`, `PROVIDER_ERROR`, `SERVER_ERROR`):** تعطل خدمة المزود (Anthropic, OpenAI, Gemini) أو انقطاع الشبكة.
2. **أعطال الحصص والمعدلات (`RATE_LIMITED`, `QUOTA_EXHAUSTED`, `BUDGET_EXCEEDED`):** تجاوز عدد الطلبات في الدقيقة أو نفاد الرصيد.
3. **أخطاء البنية والاستجابة (`INVALID_JSON`, `INVALID_STRUCTURE`):** رد النموذج بنصوص غير متوافقة مع مخطط الـ JSON المطلوب.
4. **أخطاء المحتوى والسلامة (`CONTENT_BLOCKED`):** اعتراض فلاتر الأمان للمستند أو النص.
5. **أعطال الملفات الفيزيائية (`FILE_CORRUPTED`, `FILE_OVERSIZED`):** ملف تالف، محمي بكلمة مرور، أو تجاوز الحجم الأقصى المسموح (8MB).

### 7.2 السلوك الإلزامي عند التعطل (Graceful Degradation Protocol):
* **تأمين حالة التذكرة:** تبقى التذكرة في حالة `قيد التحليل` (`Analyzing`)، وتُوسم المستندات المتعذرة بـ `بحاجة لمراجعة يدوية`.
* **حظر إرباك العميل:** **يُمنع منعاً باتاً** نقل التذكرة إلى `بانتظار مستندات` (`AwaitingDocs`)؛ لأن الخلل في النظام الداخلي وليس نقصاً من العميل. يُرسل للعميل إشعار مطمئن بأن طلبه قيد المراجعة البشرية.
* **التصعيد البشري الفوري (Human Escalation):** إرسال تنبيه فوري في لوحة موظفي الاستقبال لمراجعة المستند يدوياً بالعين المجردة (`TicketTriage::requestHuman`).
* **السرية التامة للأخطاء (Zero Leakage):** يُحظر عرض نصوص أخطاء الـ API ومفاتيح المزود للمستخدم أو في واجهات React. تُسجل التفاصيل التقنية مشفرة في جدول `ai_runs` مربوطة برمز تتبع `trace_id`.
* **إتاحة زر إعادة التشغيل للموظف (`rerun`):** تزويد لوحة موظف الاستقبال بزر لإعادة فحص المستندات آلياً بعد زوال العطل التقني للمزود.

## 8. خارطة الطريق التنفيذية عبر المرحلتين (Implementation Roadmap)

خطة العمل المعتمدة لنقل المنصة بالكامل إلى نمط DDD الخالص:

### المرحلة الأولى: بناء وتوثيق خلفية النظام (Backend DDD Overhaul)
1. **الخطوة 1: معيارية الحالات والصلاحيات في قاعدة البيانات (Enum & DB Migration):**
   * تحديث كتالوجات الـ Enums لدعم القيم الإنجليزية مع دوال التسمية العربية (`clientLabel()`, `label()`).
   * كتابة سكربت ترحيل بيانات آمن (Safe Data Migration) لتحديث الصفوف القائمة في الجداول دون توقف الخدمة.
2. **الخطوة 2: عزل وبناء طبقة المجال الصرفة (Pure Domain Layer):**
   * إنشاء كائن الدومين الصافي `TicketEntity` وكائنات القيمة (`TicketNumber`, `TicketType`, `ClosureReason`) بلغة PHP الصرفة دون أي اعتماد على Eloquent.
   * تعريف واجهة المستودع المجردة `TicketRepositoryInterface` وتطبيقها في الـ Infrastructure عبر `EloquentTicketRepository`.
   * كبسولة قواعد التحقق وحساب الصلاحيات داخل كائن الدومين الصرف، وحفظ استقلالية منطق الأعمال.
3. **الخطوة 3: توحيد وتوسيع محرك الانتقالات (`Workflow Engine`):**
   * إلحاق كافة الانتقالات في القضايا، التنفيذ، الاستشارات، والفواتير بمحرك `Workflow::run()`.
   * تفعيل القفل التشاؤمي `lockForUpdate()` على مستوى كافة الكيانات.
4. **الخطوة 4: مصفوفة الإجراءات التقريرية الموحدة (`Server-Driven Actions Matrix`):**
   * تضمين مصفوفة `actions` الصريحة في كل استجابة لكيان (تذكرة، استشارة، قضية، تنفيذ، فاتورة).
5. **الخطوة 5: نظام تدقيق الصلاحيات وسجلات الرحلة (Audit & Security):**
   * ضبط سياسات الـ Policies والـ Guards وتأكيد فحص سياق الملكية (ABAC) في كافة نقاط الدخول.

### المرحلة الثانية: إعادة بناء وتكامل الواجهة الأمامية (Frontend Inertia/React Overhaul)
1. **الخطوة 1: تطهير الواجهة من الشروط العربية (Zero Arabic Logic Invariant):**
   * فحص شامل لكافة ملفات `resources/js/pages/` و `resources/js/components/`.
   * استبدال كافة المقارنات النصية العربية (`status === 'جديدة'`) بمقارنات مع Enums موحدة ومكتوبة بالإنجليزية المستوردة من تعريفات الأنواع `@/types`.
2. **الخطوة 2: اعتماد العرض القائم على مصفوفة الإجراءات (`Action-Driven UI`):**
   * إعادة صياغة أشرطة الأزرار والعمليات لتقرأ مباشرة من `item.actions.can_*`.
   * منع أي شرط تركيبي طويل في الواجهة لحساب إمكانية ظهور الزر.
3. **الخطوة 3: التنقل الآمن والروابط العميقة (Deep Inertia Links):**
   * استبدال وسوم `<a>` التقليدية بمكون `<Link>` من `@inertiajs/react` للحفاظ على حالة التطبيق وسرعته.
   * ربط العمليات بالانتقال المباشر إلى صفحة السجل المنشأ حديثاً (`/cases/{id}`) بدلاً من قوائم الفهرس.
4. **الخطوة 4: التوحيد البصري للشارات والنغمات (Tone & Badge Consistency):**
   * استهلاك دالة نغمة الحالة (`tone`) المصدرة من الخادم لضمان تطابق الألوان (Amber, Blue, Green, Cyan, Grey, Red) عبر كافة اللوحات.
5. **الخطوة 5: واجهات التعافي من أعطال الذكاء الاصطناعي (Resilience UX):**
   * إظهار شارات "قيد الفحص اليدوي" المطمئنة للعميل، وتفعيل زر "إعادة التحليل الآلي" في لوحة الموظف.

### 8.3 استراتيجية ترحيل ومعايشة الكود القديم (Strangler Fig & Legacy Coexistence Strategy)
* **القاعدة:** يُمنع أسلوب الهدم الشامل الفجائي (Big-Bang Rewrite) منعاً لكسر النظام أو تعطيل الخدمة. يتم نقل الكود القديم تدريجياً عبر 3 مراحل محكمة:
  1. **المرحلة 1: التعايش والربط عبر المحولات (Coexistence & Repository Adapters):**
     * تبقى النماذج القديمة (`App\Models\Ticket`) والجداول والعلاقات تعمل في مساراتها القائمة بدون أي تغيير كاسر.
     * يُستخدم مستودع البنية التحتية (`EloquentTicketRepository`) كـ Adapter يربط نموذج الـ DB بكائن الدومين الصافي (`TicketEntity`) دون إحداث أي انقطاع.
     * ضمان حماية وسلامة البيانات الحالية في قاعدة البيانات (Zero Data Loss).
  2. **المرحلة 2: التفويض المنطقي والوسم بعدم الاستخدام (Delegation & Deprecation):**
     * الدوال في المتحكمات والـ Models التي كانت تحتوي على شروط أعمال مشتتة لا تُحذف فوراً، بل يُعدل تنفيذها الداخلي ليفوّض المنطق إلى كائن الدومين الصافي (`TicketEntity`).
     * تمييز الدوال القديمة المراد إيقافها بوسم `@deprecated` لتنبيه المطورين والوكلاء بعدم استخدامها مجدداً.
  3. **المرحلة 3: التنظيف الآمن للأكواد الميتة (Safe Clean-up & Pruning):**
     * بعد اكتمال ربط كافة شاشات الواجهة الأمامية بالمعمارية الجديدة واجتياز حزمة الاختبارات الشاملة بنسبة 100%، يتم حذف الأكواد القديمة غير المستخدمة بأمان تام.

## 9. محاذير معمارية ممنوعة قطعياً (Strict Architectural Anti-Patterns)

1. ❌ **منع التعديل المباشر لحقول الحالة:**
   ```php
   // ❌ ممنوع قطعياً ومرفوض
   $ticket->update(['status' => TicketStatus::ReadyForOutcome]);

   // ✅ الطريقة الوحيدة المعتمدة
   Workflow::run(new ReadyForOutcome, $ticket, $actor);
   ```

2. ❌ **منع الشروط المبنية على نصوص عربية في الواجهة الأمامية:**
   ```typescript
   // ❌ ممنوع قطعياً في ملفات React/TypeScript
   if (ticket.status === 'قيد التحليل') { ... }

   // ✅ الطريقة المعتمدة
   if (ticket.status === TicketStatus.Analyzing || ticket.actions.can_request_docs) { ... }
   ```

3. ❌ **منع ارتداد الحالات للوراء عند رفض المقترح الإداري:**
   عند رفض مقترح مآل التذكرة من الإدارة العليا، تعود التذكرة للحالة السابقة المباشرة (`ReadyForOutcome`)، ويُحظر إرجاعها إلى `LegalOpinion` لمنع ضياع أثر ومخرجات الجلسة الاستشارية المنجزة.

4. ❌ **منع تجاوز قفل الصف عند التحويل (Race Conditions):**
   أي عملية تحويل لقضية أو تنفيذ يجب أن تقفل التذكرة أولاً:
   ```php
   Ticket::whereKey($ticket->id)->lockForUpdate()->firstOrFail();
   ```
   وفحص عدم وجود قضية منشأة مسبقاً لنفس التذكرة قبل البدء.

5. ❌ **منع تكرار منطق العمليات في عدة متحكمات:**
   منطق الإجراء يُكتب لمرة واحدة فقط داخل خدمة التطبيق المعتمدة (`Domain/Application Service`)، ويُستدعى في كافة اللوحات (موظف، محامي، إدارة).

6. ❌ **منع تسريب تفاصيل وأسرار أخطاء الذكاء الاصطناعي للعميل:**
   يُحظر تمرير رسائل الخطأ الناتجة عن مزودي الـ AI أو أكواد الـ API في ردود الـ JSON الموجهة للمتصفح.

7. ❌ **منع الروابط العامة غير العميقة بعد التحويل:**
   روابط التحويل بعد إنشاء قضية أو ملف تنفيذ يجب أن تنقل المستخدم فوراً لسجل الكيان الجديد (`/cases/{id}`) وليس لقائمة الفهرس العامة (`/cases`).

8. ❌ **منع استخدام وسوم التنقل التقليدية `<a>`:**
   يجب استخدام مكون `<Link>` التابع لـ Inertia لتجنب إعادة تحميل الصفحة الكامل وإعادة تهيئة الذاكرة وحالة الواجهة.

9. ❌ **منع سداد الفواتير غير المستحقة أو المسودات:**
   أي عملية دفع يجب أن تتحقق من استيفاء الفاتورة لشرط `isPayable()` أولاً.

10. ❌ **منع إنشاء استشارة بدون معرف التذكرة الأصلية:**
    إذا كان طلب الاستشارة ناتجاً عن دراسة تذكرة، يُلزم تمرير `ticket_id` برمجياً لمنع تفكك السجل القانوني للعميل.

11. ❌ **منع الحذف الصلب (Hard Delete) لسجلات الحركات والرحلة:**
    سجلات `journey_transitions` و `audit_logs` غير قابلة للحذف نهائياً (Append-Only Audit Trail).

12. ❌ **منع تخمين ظهور الأزرار في الواجهة:**
    تعتمد شاشات React بالكامل على مصفوفة الإجراءات الصريحة `actions` القادمة من الـ Backend.

## 10. ميثاق الجودة والاختبارات القياسية (Architectural Testing Standard)

قبل اعتماد أي ميزة أو تعديل على دورات حياة النطاقات، يجب أن تجتاز حزمة الاختبارات الآلية الثلاثية:

### 1. اختبار سلامة الانتقالات والتدقيق (Transition & Audit Integrity Test):
* التحقق من قفل الصف.
* التحقق من تحديث الحالة بصورة صحيحة.
* التحقق من إنشاء سجل موثق في `journey_transitions` يحوي معرف الفاعل والحالة المصدر والهدف.
* التحقق من إطلاق الأحداث بعد الالتزام (`DB::afterCommit`).

### 2. اختبار حراس الصلاحيات ومنع الاختراق (Guards & Authorization Test):
* التحقق من رمي `TransitionDenied` برمز 403 عند محاولة مستخدم غير مصرح تنفيذ الإجراء.
* التحقق من رمي `TransitionDenied` برمز 422 عند محاولة تنفيذ انتقال من حالة غير مقبولة أو ببيانات ناقصة.

### 3. اختبار التجميد القطعي (Immutability Freeze Test):
* التحقق من رفض أي تعديل أو انتقال جديد على أي تذكرة أو سجل تم تجميده (`is_frozen = true`) بعد تحويله لمآله النهائي.

### 4. حارس عدم عودة الحالات الملغاة (`RetiredStatusesStayGoneTest`):
* فحص آلي دائم يضمن عدم عودة أي حالات قديمة تم إلغاؤها بقرارات الإدارة والمعمارية البرمجية.
